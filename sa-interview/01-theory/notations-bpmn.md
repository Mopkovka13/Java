# BPMN — нотация моделирования бизнес-процессов

**BPMN (Business Process Model and Notation)** — стандарт для описания бизнес-процессов. Активно используется в банках (в т.ч. Сбер). Спрашивают часто.

---

## Основные группы элементов

### 🟢 Вопрос: Из каких элементов состоит BPMN?

1. **Объекты потока (Flow Objects):**
   - **События (Events)** — кружки. Начальное (тонкая обводка), промежуточное (двойная), конечное (жирная).
   - **Действия/Задачи (Activities)** — прямоугольники со скруглением.
   - **Шлюзы (Gateways)** — ромбы (ветвление/слияние).

2. **Соединяющие объекты (Connecting Objects):**
   - **Поток управления (Sequence Flow)** — сплошная стрелка (порядок действий).
   - **Поток сообщений (Message Flow)** — пунктирная стрелка (обмен между участниками).
   - **Ассоциация** — точечная линия (связь с артефактами).

3. **Зоны ответственности (Swimlanes):**
   - **Пул (Pool)** — участник процесса (организация/система).
   - **Дорожка (Lane)** — роль/подразделение внутри пула.

4. **Артефакты (Artifacts):**
   - **Объект данных (Data Object)**, **Группа**, **Текстовая аннотация**.

---

## Ключевые различия (любимые вопросы)

### 🟢 Вопрос: Чем пул отличается от дорожки?

- **Пул (Pool)** — отдельный участник процесса (например, «Банк» и «Клиент» — два пула). Между пулами общение **только через Message Flow** (пунктир).
- **Дорожка (Lane)** — подразделение/роль **внутри одного пула** (например, внутри пула «Банк»: дорожки «Фронт-офис», «Бэк-офис», «Антифрод»). Между дорожками работает **Sequence Flow** (сплошная).

### 🟢 Вопрос: Чем Sequence Flow отличается от Message Flow?

- **Sequence Flow** (сплошная стрелка) — последовательность шагов **внутри одного пула**.
- **Message Flow** (пунктирная стрелка) — обмен сообщениями **между разными пулами**. Нельзя соединять Sequence Flow два пула.

## Шлюзы (Gateways)

### 🟡 Вопрос: Какие бывают шлюзы в BPMN?

- **Эксклюзивный (XOR)** — ромб с «X» или пустой. Выбирается **ровно один** путь по условию (если/иначе).
- **Параллельный (AND)** — ромб с «+». Запускаются **все** ветви одновременно, далее синхронизация.
- **Инклюзивный (OR)** — ромб с «O». Может пойти **один или несколько** путей по условиям.
- **Событийный (Event-based)** — ромб с пятиугольником. Путь выбирается по тому, **какое событие наступит первым** (например, пришёл ответ или сработал таймаут).

> ⚠️ Важно: если разветвил параллельным шлюзом — нужно собрать тем же параллельным. Не смешивай типы на разветвлении/слиянии.

### 🟡 Вопрос: Какие бывают события?

**По расположению:** начальные / промежуточные / конечные.
**По типу:**
- **Сообщение (Message)** — конверт (получение/отправка).
- **Таймер (Timer)** — часы (ожидание / по расписанию).
- **Ошибка (Error)** — молния (обработка ошибок).
- **Сигнал, условие, эскалация, отмена** и др.

Пример: промежуточное событие-таймер «ждать 24 часа», граничное событие-ошибка на задаче «при сбое перейти к компенсации».

## Задачи (типы Activity)

### 🟡 Вопрос: Какие типы задач бывают?

- **User Task** — выполняет человек через интерфейс (иконка человечка).
- **Service Task** — автоматическая, выполняет система/сервис (шестерёнка).
- **Script Task** — выполнение скрипта.
- **Send/Receive Task** — отправка/получение сообщения.
- **Manual Task** — ручная работа без системы.
- **Business Rule Task** — обращение к движку бизнес-правил.
- **Call Activity / Sub-Process** — вызов подпроцесса (свёрнутый блок с «+»).

## Практика

### 🟡 Кейс: Опиши процесс «Оформление кредитной заявки» в BPMN

```
Пул "Банк"
  [Старт: получена заявка]
      → (User Task) Менеджер проверяет документы
      → <XOR: документы полные?>
           — нет → (User Task) Запросить документы → возврат
           — да  → (Service Task) Отправить запрос в скоринг ─ ─ ─> [Пул "Скоринговая система"]
      → <Event-based: ждём ответ или таймаут>
           — пришёл ответ → <XOR: одобрено?>
                — да  → (Service Task) Создать договор → [Конец: одобрено]
                — нет → (User Task) Уведомить клиента → [Конец: отказ]
           — таймаут 24ч → (User Task) Эскалация
```

### Лучшие практики BPMN

- Один процесс — одна **start**-точка (по возможности), несколько **end** допустимо.
- Называй задачи в формате **«Глагол + объект»**: «Проверить документы», «Создать договор».
- Не смешивай типы шлюзов при разветвлении/слиянии.
- Взаимодействие между участниками — через Message Flow и отдельные пулы.
- Не перегружай диаграмму — выноси детали в подпроцессы.
- Уровни: контекстная диаграмма → процесс верхнего уровня → подпроцессы.
