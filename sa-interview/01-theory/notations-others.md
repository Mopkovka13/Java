# Прочие нотации: ERD, DFD, IDEF0, C4

---

## ERD — Entity-Relationship Diagram

### 🟢 Вопрос: Что такое ERD?

Диаграмма «сущность-связь» — модель данных: какие сущности есть и как они связаны. Основа проектирования БД.

**Элементы:**
- **Сущность (Entity)** — объект (Клиент, Заказ, Товар).
- **Атрибуты** — свойства (id, имя, дата).
- **Связи (Relationships)** с кардинальностью.

### 🟢 Вопрос: Какие бывают типы связей?

- **Один к одному (1:1)** — паспорт ↔ человек.
- **Один ко многим (1:N)** — клиент → его заказы.
- **Многие ко многим (M:N)** — студенты ↔ курсы (реализуется через **связующую/промежуточную таблицу**).

### 🟡 Вопрос: Как реализовать M:N в реляционной БД?

Через **junction-таблицу** (таблицу-связку) с двумя внешними ключами:
```
Student (id, name)
Course (id, title)
StudentCourse (student_id FK, course_id FK)  -- связующая
```

### 🟡 Нотации ERD

- **Crow's Foot («вороньи лапки»)** — самая популярная: «лапка» = много, палочка = один, кружок = необязательно.
- **Chen** — академическая (ромбы для связей).
- **IDEF1X** — в госстандартах.

## DFD — Data Flow Diagram

### 🟡 Вопрос: Что такое DFD?

Диаграмма потоков данных — показывает, как данные движутся между процессами, хранилищами и внешними сущностями. Не показывает последовательность/время (в отличие от BPMN/sequence), показывает **потоки данных**.

**Элементы:** внешние сущности (источники/приёмники), процессы, хранилища данных, потоки данных. Бывают уровни: контекстная диаграмма (уровень 0) → детализация.

## IDEF0

### 🟡 Вопрос: Что такое IDEF0?

Методология функционального моделирования. Каждый блок (функция) имеет 4 стороны:
- **Вход (Input)** — слева (что преобразуется);
- **Выход (Output)** — справа (результат);
- **Управление (Control)** — сверху (правила, регламенты);
- **Механизм (Mechanism)** — снизу (ресурсы, исполнители).

Принцип ICOM. Используется в госсекторе и для регламентации процессов «as-is/to-be».

## C4 — модель архитектуры

### 🟡 Вопрос: Что такое модель C4?

Подход к описанию архитектуры ПО на 4 уровнях детализации (от общего к частному):
1. **Context** — система и её окружение (пользователи, внешние системы).
2. **Container** — приложения/сервисы/БД внутри системы (например, веб-приложение, API, БД, очередь).
3. **Component** — компоненты внутри контейнера.
4. **Code** — классы (редко, обычно генерится).

Удобно для описания микросервисной архитектуры. Senior-аналитику полезно владеть уровнями Context и Container.

## Сравнение: что когда применять

| Задача | Нотация |
|--------|---------|
| Бизнес-процесс «как идёт работа» | **BPMN** |
| Взаимодействие сервисов во времени | **UML Sequence** |
| Функции системы и кто пользуется | **UML Use Case** |
| Модель данных / структура БД | **ERD** |
| Жизненный цикл сущности (статусы) | **UML State Machine** |
| Архитектура системы (уровни) | **C4** |
| Потоки данных между процессами | **DFD** |
| Регламентация функций (госсектор) | **IDEF0** |
| Структура классов/сущностей | **UML Class** |

### 🔴 Вопрос: Как выбрать нотацию для задачи?

От аудитории и цели:
- бизнесу/менеджерам — BPMN, контекстная C4 (понятно без техники);
- разработчикам — sequence, class, ERD, container C4;
- для согласования логики — activity/state.
Главное — нотация это инструмент коммуникации, выбирай ту, что поймёт читатель.
