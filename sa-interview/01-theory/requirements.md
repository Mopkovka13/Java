# Требования: виды, сбор, документирование

Это **ядро профессии**. Спрашивают почти всегда. Учить досконально.

---

## Классификация требований

### 🟢 Вопрос: Какие бывают виды требований?

**По уровню:**
- **Бизнес-требования** — зачем проект бизнесу, цели, ценность (BRD).
- **Пользовательские требования** — что пользователь хочет делать в системе (User Story, use cases).
- **Системные/функциональные требования** — что конкретно система должна делать (SRS).

**По характеру:**
- **Функциональные (FR)** — ЧТО система делает: функции, поведение, реакции на действия. Пример: «Система должна позволять пользователю сбросить пароль по email».
- **Нефункциональные (NFR)** — КАК система работает: производительность, надёжность, безопасность, удобство. Пример: «Страница должна загружаться менее чем за 2 секунды при 1000 одновременных пользователей».

Подробно про NFR — [02-tech/nfr.md](../02-tech/nfr.md).

### 🟢 Вопрос: Приведи примеры функциональных и нефункциональных требований.

| Функциональные | Нефункциональные |
|---|---|
| Пользователь может оплатить заказ картой | Оплата проходит за ≤ 3 сек |
| Система отправляет SMS с кодом | Доступность системы 99,9% |
| Админ может заблокировать пользователя | Данные шифруются по ГОСТ/TLS |
| Формируется отчёт в PDF | Поддержка 10 000 RPS |

## Свойства качественного требования

### 🟡 Вопрос: Каким должно быть хорошее требование?

Критерии (по INVEST / классике):
- **Полнота** — описывает всё необходимое.
- **Непротиворечивость** — не конфликтует с другими требованиями.
- **Однозначность** — нельзя трактовать по-разному. ❌ «быстро», «удобно» — плохо.
- **Проверяемость (тестируемость)** — можно проверить выполнение.
- **Реализуемость** — технически и по ресурсам выполнимо.
- **Трассируемость** — связь с источником и с реализацией/тестами.
- **Приоритизированность** — понятна важность.

**INVEST** (для User Story): **I**ndependent, **N**egotiable, **V**aluable, **E**stimable, **S**mall, **T**estable.

### 🟡 Вопрос: Что не так с требованием «Система должна работать быстро»?

Не однозначно и не проверяемо. Нет метрики. Правильно: «95% запросов на получение баланса обрабатываются за ≤ 500 мс при нагрузке 500 RPS».

## Сбор требований (eliciation)

### 🟡 Вопрос: Какие техники сбора требований ты знаешь?

- **Интервью** — глубинная беседа со стейкхолдером.
- **Анкетирование/опросы** — для большого числа пользователей.
- **Воркшопы / мозговой штурм** — групповая выработка.
- **Наблюдение (shadowing)** — смотрим, как работает пользователь.
- **Анализ документов** — изучение существующих регламентов, систем.
- **Прототипирование** — макеты для уточнения видения.
- **Анализ конкурентов / бенчмаркинг**.
- **Brainstorming, MoSCoW-приоритизация**.

### 🟡 Вопрос: Заказчик сам не знает, что хочет. Твои действия?

1. Начать с **проблемы и цели**, а не решения («какую боль закрываем?»).
2. Показать **прототипы/макеты** — на конкретном проще реагировать.
3. Изучить **текущий процесс** (as-is) и аналоги/конкурентов.
4. Декомпозировать на маленькие гипотезы, проверять итеративно (MVP).
5. Фиксировать договорённости письменно и согласовывать.

## Приоритизация

### 🟡 Вопрос: Как приоритизируешь требования?

- **MoSCoW**: Must / Should / Could / Won't have.
- **Kano**: базовые / ожидаемые / восхищающие.
- **RICE**: Reach × Impact × Confidence / Effort.
- **Value vs Effort** (матрица ценность/трудозатраты).

## Документирование требований

### 🟢 Вопрос: Какие документы готовит аналитик?

- **BRD** (Business Requirements Document) — бизнес-требования.
- **SRS** (Software Requirements Specification) — спецификация требований к ПО.
- **FSD** (Functional Specification Document) — функциональная спецификация.
- **ТЗ** — техническое задание (часто по ГОСТ 34/19 в госсекторе и банках).
- **User Story + Acceptance Criteria** — в Agile.
- **Use Case** — сценарии использования.
- **API-контракты** (OpenAPI/Swagger), модель данных (ERD).

### 🟢 Вопрос: Как пишется User Story?

**Формат:**
```
Как <роль>,
я хочу <действие/возможность>,
чтобы <ценность/цель>.
```
**Пример:**
> Как клиент банка, я хочу видеть историю операций по счёту, чтобы контролировать свои расходы.

К User Story прилагаются **критерии приёмки** (Acceptance Criteria).

### 🟡 Вопрос: Что такое критерии приёмки и как их пишут (Gherkin)?

Критерии приёмки — условия, при которых задача считается выполненной. Часто пишут в формате **Gherkin (Given-When-Then)**:

```gherkin
Сценарий: Успешный вход по корректному паролю
  Дано пользователь находится на странице входа
  И у пользователя есть активный аккаунт
  Когда он вводит корректные логин и пароль
  И нажимает "Войти"
  Тогда он попадает в личный кабинет
  И видит сообщение "Добро пожаловать"

Сценарий: Блокировка после 5 неверных попыток
  Дано пользователь ввёл неверный пароль 4 раза
  Когда он вводит неверный пароль в 5-й раз
  Тогда аккаунт блокируется на 15 минут
  И отправляется уведомление на email
```

### 🟡 Вопрос: Чем Use Case отличается от User Story?

| User Story | Use Case |
|---|---|
| Короткая, 1–2 предложения | Подробный сценарий с шагами |
| Agile | Чаще Waterfall/RUP |
| «Что и зачем» | «Как именно», включая альтернативные потоки |
| + критерии приёмки | + основной/альтернативные/исключительные сценарии |

Структура Use Case: актёр, предусловия, основной поток, альтернативные потоки, исключения, постусловия.

## Управление требованиями

### 🔴 Вопрос: Что такое трассируемость требований?

**Traceability** — возможность проследить требование от источника (бизнес-цель) через реализацию (код/компонент) до проверки (тест-кейс). Делается через **матрицу трассируемости (RTM)**. Зачем: контроль покрытия, анализ влияния изменений (impact analysis), аудит.

### 🔴 Вопрос: Как управляешь изменениями требований?

- **Change Request** — формальная заявка на изменение.
- Оценка влияния (impact analysis): что затронется, сколько стоит.
- Версионирование требований и документации.
- Согласование со стейкхолдерами, обновление RTM.
- Baseline — зафиксированная версия требований.

### 🔴 Вопрос: Что такое BABOK?

**BABOK (Business Analysis Body of Knowledge)** — свод знаний по бизнес-анализу от IIBA. Описывает области знаний: планирование БА, выявление требований, управление жизненным циклом требований, анализ стратегии, анализ требований и дизайн решений, оценка решения. Хорошо упомянуть как методологическую базу.

## Чит-лист по требованиям

- Различай уровни: бизнес → пользовательские → системные.
- FR = что делает, NFR = насколько хорошо.
- Хорошее требование: однозначное + проверяемое.
- User Story: «Как… хочу… чтобы…» + Acceptance Criteria (Gherkin).
- Приоритизация: MoSCoW/RICE.
- Изменения: через Change Request + impact analysis.
