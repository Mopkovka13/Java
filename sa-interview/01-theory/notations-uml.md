# UML — унифицированный язык моделирования

**UML (Unified Modeling Language)** — язык для визуального моделирования систем. Для аналитика важнее всего: **sequence, class, use case, activity, state**.

---

## Классификация диаграмм

### 🟢 Вопрос: Какие типы диаграмм есть в UML?

UML делится на 2 группы (всего 14 диаграмм):

**Структурные (статика):**
- **Class** — классы, атрибуты, связи (часто как модель данных/доменная модель).
- **Component** — компоненты системы.
- **Deployment** — размещение на инфраструктуре.
- Object, Package, Composite Structure, Profile.

**Поведенческие (динамика):**
- **Use Case** — варианты использования (актёры и функции).
- **Sequence** — последовательность сообщений между объектами во времени. ⭐ для интеграций.
- **Activity** — поток действий (похоже на блок-схему/BPMN).
- **State Machine** — состояния объекта и переходы.
- Communication, Timing, Interaction Overview.

### 🟢 Вопрос: Какие диаграммы чаще всего использует аналитик?

1. **Sequence** — описание взаимодействия сервисов/систем (самая частая на собесе).
2. **Use Case** — функции системы и кто ими пользуется.
3. **Class** — модель данных/сущности.
4. **Activity** — алгоритм/бизнес-логика.
5. **State** — жизненный цикл сущности (статусы заказа, заявки).

## Sequence-диаграмма ⭐

### 🟡 Вопрос: Расскажи про sequence-диаграмму.

Показывает **обмен сообщениями между участниками во времени** (время идёт сверху вниз).

**Элементы:**
- **Lifeline** — вертикальная линия жизни участника (актёр/система/сервис).
- **Activation bar** — прямоугольник активности (когда участник что-то делает).
- **Сообщения (стрелки):**
  - сплошная стрелка с заполненным наконечником — **синхронный** вызов;
  - сплошная с открытым наконечником — **асинхронное** сообщение;
  - пунктирная — **ответ (return)**.
- **Фреймы (фрагменты):** `alt` (если/иначе), `opt` (опционально), `loop` (цикл), `par` (параллельно).

### 🟡 Кейс: Sequence для «Оплата заказа картой»

```
Клиент      Frontend        OrderService     PaymentGW       Bank
  │            │                 │               │             │
  │ оплатить   │                 │               │             │
  ├───────────>│                 │               │             │
  │            │ createPayment   │               │             │
  │            ├────────────────>│               │             │
  │            │                 │ charge(card)  │             │
  │            │                 ├──────────────>│             │
  │            │                 │               │ authorize   │
  │            │                 │               ├────────────>│
  │            │                 │               │<─ ─ ─ ─ ─ ─ │ approved
  │            │                 │<─ ─ ─ ─ ─ ─ ─ │ ok          │
  │            │   alt [успех]   │               │             │
  │            │<─ ─ ─ ─ ─ ─ ─ ─ │ "Оплачено"    │             │
  │<─ ─ ─ ─ ─ ─│                 │               │             │
  │            │   [ошибка] → показать ошибку, статус FAILED   │
```

## Use Case-диаграмма

### 🟢 Вопрос: Что показывает Use Case-диаграмма?

Функциональность системы с точки зрения пользователей.
- **Актёр** (человечек) — роль, взаимодействующая с системой.
- **Use Case** (овал) — вариант использования (функция).
- **Связи:** ассоциация (актёр—UC), `<<include>>` (всегда включает другой UC), `<<extend>>` (опциональное расширение), обобщение (наследование).

Пример: актёр «Клиент» → use cases «Войти», «Просмотреть баланс», «Сделать перевод». «Сделать перевод» `<<include>>` «Подтвердить по SMS».

### 🟡 Вопрос: Чем отличаются include и extend?

- **`<<include>>`** — обязательное включение, базовый UC всегда использует включаемый (например, «Оформить заказ» всегда включает «Авторизоваться»).
- **`<<extend>>`** — необязательное расширение при условии (например, «Оформить заказ» может расширяться «Применить промокод»).

## Class-диаграмма

### 🟡 Вопрос: Расскажи про class-диаграмму и виды связей.

Класс = прямоугольник из 3 секций: имя / атрибуты / методы.

**Виды связей:**
- **Ассоциация** — обычная связь (линия).
- **Агрегация** (пустой ромб) — «часть-целое», части живут отдельно (отдел и сотрудники).
- **Композиция** (закрашенный ромб) — сильная связь, часть не существует без целого (заказ и его позиции).
- **Наследование/обобщение** (треугольная стрелка) — «является» (is-a).
- **Зависимость** (пунктир) — использует.

**Кратность (множественность):** `1`, `0..1`, `1..*`, `*` — сколько объектов участвует в связи.

## State Machine (диаграмма состояний)

### 🟡 Вопрос: Когда применяешь диаграмму состояний?

Когда у сущности есть **жизненный цикл со статусами**. Пример — статусы заказа:

```
[Создан] → [Оплачен] → [Собран] → [Отправлен] → [Доставлен]
    │           │
    └──> [Отменён] <──┘
```

Показывает состояния, переходы, события-триггеры и условия (guards). Полезно для платежей, заявок, заказов.

## Activity-диаграмма

### 🟡 Вопрос: Чем activity-диаграмма отличается от BPMN?

Activity — это UML-аналог блок-схемы: действия, ветвления (ромбы), параллельность (синхронизирующие планки), начальная/конечная точки, swimlanes. BPMN более богат для **бизнес-процессов** (события, типы задач, межсистемное взаимодействие), Activity — более «программная» логика. На практике для процессов чаще BPMN, для алгоритма внутри функции — Activity.
