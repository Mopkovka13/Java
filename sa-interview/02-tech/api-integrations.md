# API и интеграции

Второй по частоте технический блок после SQL. Особенно REST.

---

## Основы

### 🟢 Вопрос: Что такое API?

**API (Application Programming Interface)** — контракт/интерфейс взаимодействия между программами. Определяет, как один сервис может запросить данные/действие у другого: какие методы, параметры, форматы, ошибки.

### 🟢 Вопрос: Какие стили/протоколы интеграции знаешь?

- **REST** — над HTTP, ресурсный подход, JSON. Самый распространённый.
- **SOAP** — XML, строгий контракт (WSDL), enterprise/legacy, банки.
- **GraphQL** — клиент сам запрашивает нужные поля одним запросом.
- **gRPC** — бинарный (Protobuf) поверх HTTP/2, быстрый, для микросервисов.
- **WebSocket** — двусторонняя связь в реальном времени.
- **Брокеры сообщений** (Kafka, RabbitMQ) — асинхронная интеграция (см. [messaging.md](messaging.md)).
- **Файловый обмен / SFTP / batch** — legacy, выгрузки реестров (частое в банках).

## REST

### 🟢 Вопрос: Что такое REST? Какие принципы?

**REST (Representational State Transfer)** — архитектурный стиль для веб-API поверх HTTP. Принципы:
- **Клиент-сервер** — разделение ответственности.
- **Stateless (без состояния)** — каждый запрос самодостаточен, сервер не хранит сессию между запросами.
- **Кэшируемость**.
- **Единообразие интерфейса** — ресурсы и стандартные методы.
- **Многоуровневость**.
- Ресурсы адресуются URI: `/users/123/orders`.

### 🟢 Вопрос: Какие HTTP-методы используются в REST?

| Метод | Назначение | Идемпотентный | Безопасный |
|-------|-----------|:---:|:---:|
| **GET** | получить ресурс | ✅ | ✅ |
| **POST** | создать ресурс | ❌ | ❌ |
| **PUT** | заменить ресурс целиком | ✅ | ❌ |
| **PATCH** | частично обновить | ❌* | ❌ |
| **DELETE** | удалить | ✅ | ❌ |

*PATCH может быть идемпотентным в зависимости от реализации.

### 🟢 Вопрос: Какие коды ответов HTTP знаешь?

- **2xx — успех:** 200 OK, 201 Created, 202 Accepted, 204 No Content.
- **3xx — перенаправление:** 301 Moved Permanently, 304 Not Modified.
- **4xx — ошибка клиента:** 400 Bad Request, 401 Unauthorized (не аутентифицирован), 403 Forbidden (нет прав), 404 Not Found, 405 Method Not Allowed, 409 Conflict, 422 Unprocessable Entity, 429 Too Many Requests.
- **5xx — ошибка сервера:** 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout.

### 🟡 Вопрос: В чём разница 401 и 403?

- **401 Unauthorized** — не аутентифицирован (не знаем, кто ты; нет/невалидный токен).
- **403 Forbidden** — аутентифицирован, но **нет прав** на действие.

### 🟡 Вопрос: Что такое идемпотентность? Зачем она в API?

**Идемпотентность** — повторный одинаковый запрос даёт тот же результат, что и один (не создаёт дублей, не списывает дважды). GET/PUT/DELETE идемпотентны, POST — нет.

**Зачем:** при сетевых сбоях клиент может повторить запрос (retry). Без идемпотентности повтор «создать платёж» спишет деньги дважды. Решение для POST — **ключ идемпотентности** (`Idempotency-Key` в заголовке): сервер по ключу понимает, что запрос уже обработан, и возвращает прежний результат.

### 🟡 Вопрос: Как версионируют API?

- В URL: `/api/v1/users` (самое популярное).
- В заголовке: `Accept: application/vnd.api.v2+json`.
- В query-параметре: `?version=2`.
Зачем: не ломать старых клиентов при изменениях контракта.

### 🟡 Вопрос: Как реализовать пагинацию?

- **Offset/Limit:** `?limit=20&offset=40` — просто, но медленно на больших offset.
- **Keyset/Cursor:** `?after=last_id&limit=20` — эффективнее для больших данных.
- **Page-based:** `?page=3&size=20`.

### 🟡 Вопрос: Что такое OpenAPI/Swagger?

**OpenAPI (Swagger)** — стандарт описания REST API в формате YAML/JSON: эндпоинты, методы, параметры, схемы запросов/ответов, коды. По нему генерируется документация (Swagger UI), клиенты, моки. Аналитик часто **проектирует контракт API в OpenAPI** — это ценный навык.

## SOAP

### 🟡 Вопрос: Чем REST отличается от SOAP?

| | REST | SOAP |
|---|---|---|
| Формат | обычно JSON | только XML |
| Протокол | HTTP | HTTP, SMTP и др. |
| Контракт | OpenAPI (опционально) | WSDL (обязательный, строгий) |
| Гибкость | высокая, легче | строгий, тяжеловесный |
| Безопасность | HTTPS, OAuth | WS-Security (на уровне сообщения) |
| Транзакции | нет встроенных | WS-* (ACID-подобные) |
| Где | веб, мобайл, микросервисы | enterprise, банки, госуслуги, legacy |

SOAP всё ещё жив в банках и интеграциях с госсистемами (СМЭВ, ФНС и т.п.).

### 🟡 Вопрос: Что такое WSDL?

**WSDL (Web Services Description Language)** — XML-описание SOAP-сервиса: какие операции, какие параметры, типы данных, эндпоинты. Аналог OpenAPI для SOAP. По нему генерируют клиентов.

## GraphQL и gRPC

### 🟡 Вопрос: Что такое GraphQL и его плюсы/минусы?

Язык запросов к API: клиент **сам указывает, какие поля** нужны, один эндпоинт.
- ➕ нет over-fetching/under-fetching, гибко, один запрос вместо нескольких.
- ➖ сложнее кэшировать, риск тяжёлых запросов, сложнее на сервере.

### 🟡 Вопрос: Что такое gRPC и когда применять?

RPC-фреймворк от Google: бинарный формат **Protobuf** поверх **HTTP/2**, строгий контракт `.proto`, поддержка стриминга. Быстрый и компактный — хорош для **межсервисного взаимодействия внутри микросервисной системы**. Минус: не браузерный «из коробки», бинарный (сложнее дебажить).

### 🟡 Вопрос: Когда REST, когда gRPC, когда брокер?

- **REST** — публичные/внешние API, веб, мобайл, простота.
- **gRPC** — внутреннее общение микросервисов, высокая нагрузка/низкая задержка.
- **Брокер (Kafka/RabbitMQ)** — асинхронные события, развязка сервисов, пиковые нагрузки.

## Синхронные vs асинхронные интеграции

### 🟡 Вопрос: Чем отличается синхронное взаимодействие от асинхронного?

- **Синхронное** — клиент шлёт запрос и **ждёт ответ** (REST, gRPC). Просто, но связность и блокировка; при недоступности сервиса — ошибка.
- **Асинхронное** — клиент отправляет сообщение и **не ждёт** (очередь/брокер). Развязка сервисов, устойчивость к пикам, но сложнее отслеживать результат, eventual consistency.

### 🔴 Вопрос: Как проектировать интеграцию с внешним сервисом, который может «лежать»?

- **Таймауты** на запросы.
- **Retry с backoff** (повтор с нарастающей паузой) + идемпотентность.
- **Circuit Breaker** — «предохранитель», отключает вызовы при серии ошибок.
- **Fallback** — деградация (кэш/значение по умолчанию).
- **Очередь** для асинхронной обработки и сглаживания пиков.
- **Логирование и мониторинг**, корреляционные id для трассировки.
- **DLQ** (dead letter queue) для необработанных сообщений.

## Контракты и форматы

### 🟢 Вопрос: Что такое REST endpoint? Спроектируй CRUD для «заказов».

```
GET    /orders          — список заказов (с пагинацией/фильтрами)
GET    /orders/{id}     — один заказ
POST   /orders          — создать заказ
PUT    /orders/{id}     — заменить заказ
PATCH  /orders/{id}     — частично обновить (например, статус)
DELETE /orders/{id}     — удалить
GET    /orders/{id}/items — позиции заказа (вложенный ресурс)
```
Тело ответа — JSON. Ошибки — единый формат `{ "error": { "code": "...", "message": "..." } }`.

### 🟡 Best practices REST API

- Существительные во множественном числе для ресурсов (`/orders`, не `/getOrders`).
- Действия — через HTTP-методы, не в URL.
- Версионирование (`/v1`).
- Единый формат ошибок + понятные коды.
- Пагинация, фильтрация, сортировка через query-параметры.
- Идемпотентность для платёжных POST.
- HTTPS всегда, аутентификация (OAuth2/JWT — см. [protocols-formats.md](protocols-formats.md)).
- Документация (OpenAPI).
