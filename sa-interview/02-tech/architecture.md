# Архитектура систем

Для middle+ важно понимать монолит vs микросервисы, паттерны интеграции, основные компоненты.

---

## Монолит vs микросервисы

### 🟡 Вопрос: Чем монолит отличается от микросервисов?

| | Монолит | Микросервисы |
|---|---|---|
| Структура | одно приложение | много мелких сервисов |
| Деплой | целиком | независимо каждый |
| Масштабирование | всё приложение | отдельные сервисы |
| БД | обычно одна общая | у каждого своя |
| Связность | высокая | низкая |
| Сложность | проще на старте | сложнее (сеть, оркестрация) |
| Технологии | один стек | разные стеки возможны |
| Отказ | падает всё | изолированно |

### 🟡 Вопрос: Плюсы и минусы микросервисов?

**Плюсы:** независимый деплой и масштабирование, отказоустойчивость, разные технологии, автономные команды.
**Минусы:** сложность распределённой системы (сеть, задержки, частичные сбои), сложнее транзакции (нужны Saga), мониторинг и трассировка, согласованность данных (eventual consistency), накладные расходы на инфраструктуру.

### 🟡 Вопрос: Когда выбрать монолит, а когда микросервисы?

- **Монолит** — стартап/MVP, маленькая команда, простой домен, нужен быстрый старт.
- **Микросервисы** — большая система, много команд, разные требования к масштабированию частей, высокая нагрузка.
Часто начинают с **модульного монолита** и выделяют сервисы по мере роста.

## Компоненты типовой архитектуры

### 🟡 Вопрос: Из чего состоит типичная веб-система?

```
[Клиент/Браузер/Мобайл]
        ↓
[CDN] → [Load Balancer]
        ↓
[API Gateway]
        ↓
[Микросервисы] ←→ [Кэш (Redis)]
        ↓               ↓
[Базы данных]    [Брокер (Kafka)]
        ↓
[Внешние системы]
```

- **Load Balancer** — распределяет нагрузку между инстансами.
- **API Gateway** — единая точка входа: маршрутизация, аутентификация, rate limiting, агрегация.
- **Кэш (Redis)** — ускорение чтения, сессии.
- **CDN** — раздача статики ближе к пользователю.

### 🟡 Вопрос: Что такое API Gateway и зачем он?

Единая точка входа для клиентов в микросервисную систему. Делает: маршрутизацию запросов, аутентификацию/авторизацию, rate limiting, логирование, агрегацию ответов нескольких сервисов, версионирование. Клиент не знает о внутренней топологии сервисов.

### 🟡 Вопрос: Что такое балансировка нагрузки?

Распределение запросов между несколькими серверами/инстансами. Алгоритмы: Round Robin, Least Connections, по хэшу (sticky session), weighted. Цель — масштабирование и отказоустойчивость.

## Масштабирование

### 🟡 Вопрос: Чем горизонтальное масштабирование отличается от вертикального?

- **Вертикальное (scale up)** — наращиваем мощность одного сервера (CPU/RAM). Просто, но есть потолок и дорого.
- **Горизонтальное (scale out)** — добавляем серверы/инстансы. Почти безграничное, но нужна stateless-архитектура, балансировка, сложнее.

### 🔴 Вопрос: Что такое шардирование и репликация?

- **Репликация** — копии данных на нескольких узлах (master-slave). Повышает доступность и масштабирует **чтение**. Бывает синхронная/асинхронная.
- **Шардирование (sharding)** — разбиение данных по узлам по ключу (например, по диапазону client_id). Масштабирует **запись** и объём. Сложнее: кросс-шардовые запросы, ребалансировка.

## Паттерны и подходы

### 🔴 Вопрос: Что такое Circuit Breaker?

«Предохранитель»: если вызовы к сервису постоянно падают, breaker «размыкается» и быстро возвращает ошибку/fallback, не нагружая упавший сервис, давая ему восстановиться. Состояния: Closed (норма) → Open (отсекаем) → Half-Open (пробуем).

### 🔴 Вопрос: Что такое CQRS и Event Sourcing?

- **CQRS (Command Query Responsibility Segregation)** — разделение моделей для записи (commands) и чтения (queries). Можно оптимизировать и масштабировать их отдельно.
- **Event Sourcing** — хранение не текущего состояния, а **последовательности событий**, из которых состояние восстанавливается. Полный аудит, можно «отмотать». Сложнее, eventual consistency. Часто применяют в банках для аудита операций.

### 🔴 Вопрос: Что такое идемпотентность на уровне архитектуры и зачем?

Чтобы повторные запросы (retry при сбоях сети) не приводили к дублям. Реализуется ключами идемпотентности, дедупликацией, проверкой состояния. Критично для платежей. См. [api-integrations.md](api-integrations.md).

### 🔴 Вопрос: Как обеспечить согласованность данных в микросервисах?

Распределённого ACID нет. Используют:
- **Saga** (компенсирующие транзакции),
- **Outbox** (атомарность БД + событие),
- **Eventual consistency** (согласованность со временем),
- идемпотентность и дедупликацию.
См. [messaging.md](messaging.md).

## Архитектурные стили (обзор)

- **Слоистая (layered)** — presentation / business / data.
- **Гексагональная (ports & adapters)** — изоляция домена от инфраструктуры.
- **Событийно-ориентированная (event-driven)** — взаимодействие через события.
- **SOA** — сервис-ориентированная (предшественник микросервисов, ESB).
- **Serverless** — функции как сервис (FaaS).

### 🔴 Вопрос: Как описываешь архитектуру для разных аудиторий?

Через **C4** (см. [notations-others.md](../01-theory/notations-others.md)): бизнесу — Context, команде — Container/Component. Для взаимодействий — sequence. Главное — уровень детализации под читателя.
