# Брокеры сообщений (Kafka, RabbitMQ)

Асинхронная интеграция. Спрашивают на middle+, в банках почти всегда (Kafka — стандарт де-факто).

---

## Зачем нужны брокеры

### 🟡 Вопрос: Зачем нужны очереди/брокеры сообщений?

- **Развязка (decoupling)** сервисов — отправитель не знает о получателях.
- **Сглаживание пиков** — буферизация нагрузки.
- **Надёжность** — сообщение не потеряется, если получатель временно недоступен.
- **Асинхронность** — отправитель не ждёт обработки.
- **Масштабирование** — несколько консьюмеров параллельно.
- **Событийная архитектура** (event-driven).

### 🟡 Вопрос: Что такое Producer, Consumer, Broker, Topic/Queue?

- **Producer** — отправитель сообщений.
- **Consumer** — получатель/обработчик.
- **Broker** — сервер, хранящий и доставляющий сообщения.
- **Topic** (Kafka) / **Queue** (RabbitMQ) — канал/категория сообщений.

## Kafka

### 🟡 Вопрос: Как устроена Kafka?

Распределённый **лог событий**. Ключевые понятия:
- **Topic** — категория сообщений, делится на **партиции**.
- **Partition** — упорядоченная последовательность сообщений; обеспечивает параллелизм и порядок **внутри партиции**.
- **Offset** — позиция сообщения в партиции; консьюмер хранит свой offset.
- **Consumer Group** — группа консьюмеров; каждую партицию читает один консьюмер группы (масштабирование).
- **Key** — ключ сообщения определяет партицию (сообщения с одним ключом → одна партиция → сохраняется порядок).
- **Retention** — Kafka **хранит** сообщения заданное время, их можно перечитать (replay).

### 🟡 Вопрос: Гарантирует ли Kafka порядок сообщений?

Только **внутри одной партиции**. Между партициями порядок не гарантирован. Чтобы связанные события шли по порядку (например, по одному счёту) — используют **один ключ** (account_id) → попадают в одну партицию.

### 🔴 Вопрос: Какие гарантии доставки бывают?

- **At most once** — максимум один раз (может потеряться).
- **At least once** — минимум один раз (возможны дубли → нужна идемпотентность на стороне консьюмера).
- **Exactly once** — ровно один раз (сложнее, Kafka поддерживает через транзакции/idempotent producer).

На практике чаще **at least once + идемпотентная обработка**.

## RabbitMQ

### 🟡 Вопрос: Чем RabbitMQ отличается от Kafka?

| | Kafka | RabbitMQ |
|---|---|---|
| Модель | лог событий (pull) | классическая очередь (push) |
| Хранение | хранит, можно перечитать | удаляет после ack |
| Маршрутизация | по топикам/партициям | гибкая (exchange + routing key) |
| Пропускная способность | очень высокая | высокая |
| Порядок | в партиции | в очереди |
| Когда | потоки событий, big data, аналитика, event sourcing | задачи/команды, сложная маршрутизация, RPC |

### 🟡 Вопрос: Что такое Exchange в RabbitMQ?

Точка приёма сообщений, которая маршрутизирует их в очереди по правилам:
- **Direct** — по точному routing key.
- **Topic** — по шаблону (`order.*.created`).
- **Fanout** — во все привязанные очереди (broadcast).
- **Headers** — по заголовкам.

## Паттерны и проблемы

### 🟡 Вопрос: Что такое DLQ?

**Dead Letter Queue** — очередь для сообщений, которые не удалось обработать (ошибки, превышен лимит попыток). Позволяет не терять «битые» сообщения и разбирать их отдельно.

### 🔴 Вопрос: Как обеспечить идемпотентность консьюмера?

Поскольку доставка обычно at-least-once, возможны дубли. Решения:
- хранить id обработанных сообщений (dedup-таблица/кэш);
- использовать естественный идемпотентный ключ операции;
- делать операции идемпотентными по природе (UPSERT, проверка статуса перед действием).

### 🔴 Вопрос: Что такое Outbox-паттерн?

Проблема: нужно атомарно сохранить данные в БД **и** отправить событие в брокер (двойная запись ненадёжна). Решение **Transactional Outbox**: в одной транзакции пишем и бизнес-данные, и событие в таблицу `outbox`; отдельный процесс (или CDC, напр. Debezium) читает outbox и публикует в Kafka. Гарантирует, что событие отправится тогда и только тогда, когда данные сохранены.

### 🔴 Вопрос: Что такое Saga?

Паттерн управления распределённой транзакцией между микросервисами без общего ACID. Цепочка локальных транзакций; при сбое выполняются **компенсирующие** операции (откат). Виды:
- **Хореография** — сервисы реагируют на события друг друга (без центра).
- **Оркестрация** — центральный оркестратор управляет шагами.
Пример: бронирование (оплата → склад → доставка); если доставка не удалась — компенсация: вернуть товар на склад, отменить оплату.

## Чит-лист

- Брокер = развязка + асинхрон + устойчивость к пикам.
- Kafka: топики, партиции, offset, consumer group; порядок только в партиции; хранит сообщения.
- RabbitMQ: exchange + routing, удаляет после ack.
- Доставка чаще at-least-once → нужна идемпотентность.
- DLQ — для необработанных сообщений.
- Outbox — атомарность «БД + событие». Saga — распределённые транзакции с компенсациями.
