# Практические кейсы (System Design для аналитика)

На middle+ просят спроектировать систему/фичу. Оценивают **подход**, а не «правильный ответ».

---

## Универсальный алгоритм разбора кейса

При любом «спроектируй X» иди по шагам — это и есть то, что проверяют:

1. **Уточняющие вопросы** (самое важное!):
   - Кто пользователи и сценарии?
   - Какие границы задачи (что в скоупе, что нет)?
   - Нагрузка (кол-во пользователей, RPS, объём данных)?
   - Синхронно или асинхронно нужен результат?
   - Требования к согласованности/доступности?
   - Интеграции с внешними системами?
2. **Функциональные требования** — что система делает (список).
3. **Нефункциональные требования** — нагрузка, доступность, latency, безопасность.
4. **Модель данных** — основные сущности и связи (ERD).
5. **API / контракты** — основные эндпоинты.
6. **Архитектура и потоки** — компоненты, sequence основного сценария.
7. **Обработка ошибок и краевые случаи**.
8. **Трейд-оффы** — что выбрал и почему.

> ⚠️ Кандидаты-новички сразу бросаются «рисовать БД». Сильный кандидат сначала **задаёт вопросы** и фиксирует требования.

## Кейс 1: Сервис укорачивания ссылок (разминка)

**Уточнения:** объём (млн ссылок?), нужна ли аналитика кликов, кастомные алиасы, срок жизни.

**FR:** создать короткую ссылку, редирект, статистика кликов.
**NFR:** редирект быстрый (p99 < 50 мс), высокая доступность, чтений >> записей.

**Модель данных:**
```
links(id, short_code UNIQUE, original_url, created_at, expires_at, user_id)
clicks(id, link_id, clicked_at, ip, user_agent)  -- или агрегаты
```
**API:**
```
POST /links { url } → { short_code }
GET /{short_code} → 301 redirect
GET /links/{code}/stats
```
**Решения:** генерация кода (хэш/base62 от id/счётчик), кэш популярных ссылок (Redis), чтения масштабируем репликами. Клики — асинхронно в очередь, чтобы не тормозить редирект.

## Кейс 2: Перевод денег между счетами (банковский) ⭐

См. также [banking-domain.md](../03-banking/banking-domain.md).

**Уточнения:** внутрибанк или межбанк (СБП)? лимиты? валюты? синхронный ответ? нагрузка?

**FR:** валидация счетов, проверка средств, антифрод, списание+зачисление, история, уведомления.

**NFR:** идемпотентность, атомарность, строгая согласованность (CP), доступность 99,95%, RPO≈0, аудит, p95 ≤ 1.5 с.

**Модель данных:**
```
accounts(id, client_id, currency, balance, status)
transactions(id, from_acc, to_acc, amount, status, idempotency_key UNIQUE, created_at)
postings(id, transaction_id, account_id, direction, amount)  -- двойная запись
```
**API:**
```
POST /transfers
  Header: Idempotency-Key
  Body: { from, to, amount, currency }
  → 201 { transaction_id, status }
```
**Sequence (упрощённо):**
```
Клиент → API → Антифрод (синхронно при пороге)
       → BEGIN TX: списать from, зачислить to, записать постинги → COMMIT
       → publish "TransferCompleted" (outbox) → уведомления
```
**Краевые случаи:** недостаточно средств (409), счёт заблокирован (403), дубль запроса (вернуть прежний результат по idempotency_key), сбой после списания (атомарная транзакция/Saga с компенсацией), таймаут антифрода.

**Трейд-оффы:** монолитно одной БД-транзакцией — проще и надёжнее, если счета в одной БД; межбанк/распределённо — Saga + eventual consistency.

## Кейс 3: Система оформления заказа (e-commerce)

**FR:** корзина, оформление, оплата, резерв товара, статусы заказа, уведомления.

**Жизненный цикл заказа (state machine):**
```
Создан → Оплачен → Собран → Отправлен → Доставлен
   └────→ Отменён (на ранних статусах) → Возврат
```
**Потоки:** проверка наличия → резерв на складе → оплата (внешний платёжный шлюз, идемпотентно) → подтверждение → событие в брокер → склад/доставка/уведомления подписываются.

**Трейд-офф:** оплата и резерв в разных сервисах → распределённая транзакция → **Saga**: если оплата не прошла, компенсация — снять резерв.

## Кейс 4: Интеграция с внешним сервисом (например, БКИ/госуслуги)

**Вопросы:** синхронно или можно асинхронно? SLA внешнего сервиса? что делать при недоступности? согласие на ПДн?

**Решения:**
- Таймаут + retry с backoff + circuit breaker.
- Кэширование ответа (если допустимо по свежести).
- Очередь для асинхронной обработки тяжёлых/долгих запросов.
- Fallback при недоступности (отложить, ручная обработка).
- Логирование + корреляционный id, мониторинг.
- Контракт (OpenAPI/WSDL), маппинг полей, обработка форматов.

---

## Кейс 5: Уведомления (notifications)

**Каналы:** push, SMS, email, in-app. **FR:** шаблоны, выбор канала, повтор при сбое, отписки, дедупликация.

**Архитектура:** событие → брокер → notification-service → провайдеры (с retry/DLQ). Асинхронно, идемпотентно (не слать дубли), приоритеты (OTP важнее маркетинга), rate limiting.

---

## Кейс 6: Лента/история операций с высокой нагрузкой

**Проблема:** много чтений истории по счёту. **Решения:** индекс по (account_id, created_at), keyset-пагинация, кэш последних операций, реплики для чтения, при огромных объёмах — партиционирование по дате/шардирование по account_id, отдельное read-хранилище (CQRS).

## Как формулировать требования в кейсе (шаблон)

Когда просят «опиши требования», структурируй:

**User Story:**
> Как <роль>, я хочу <действие>, чтобы <ценность>.

**Критерии приёмки (Gherkin):**
```gherkin
Дано <предусловие>
Когда <действие>
Тогда <ожидаемый результат>
```

**Нефункциональные:** производительность (p95/RPS), доступность, безопасность, согласованность — с цифрами.
