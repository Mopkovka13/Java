## Требования

**Q: Функциональные vs нефункциональные требования?**
A: FR — что система делает (функции). NFR — насколько хорошо (производительность, надёжность, безопасность).

**Q: Каким должно быть хорошее требование?**
A: Однозначное, проверяемое, полное, непротиворечивое, реализуемое, трассируемое, приоритизированное.

**Q: Формат User Story?**
A: Как <роль>, я хочу <действие>, чтобы <ценность>. + критерии приёмки.

**Q: Что такое Gherkin?**
A: Given-When-Then (Дано-Когда-Тогда) — формат критериев приёмки/сценариев.

**Q: Техники сбора требований?**
A: Интервью, опросы, воркшопы, наблюдение, анализ документов, прототипирование, бенчмаркинг.

**Q: Методы приоритизации?**
A: MoSCoW, RICE, Kano, Value vs Effort.

**Q: INVEST?**
A: Independent, Negotiable, Valuable, Estimable, Small, Testable — критерии хорошей User Story.

## Методологии

**Q: Роли в Scrum?**
A: Product Owner, Scrum Master, команда разработки.

**Q: События Scrum?**
A: Planning, Daily, Review, Retrospective.

**Q: Scrum vs Kanban?**
A: Scrum — спринты, роли, фиксированный объём. Kanban — непрерывный поток, WIP-лимиты.

**Q: DoR vs DoD?**
A: DoR — готовность задачи к работе. DoD — критерии завершённости.

## Нотации

**Q: Пул vs дорожка в BPMN?**
A: Пул — отдельный участник (общение через Message Flow). Дорожка — роль внутри пула (Sequence Flow).

**Q: Типы шлюзов BPMN?**
A: XOR (один путь), AND (все параллельно), OR (один+), Event-based (по событию).

**Q: Sequence Flow vs Message Flow?**
A: Sequence — внутри пула (сплошная). Message — между пулами (пунктир).

**Q: Главные UML-диаграммы для аналитика?**
A: Sequence, Use Case, Class, Activity, State Machine.

**Q: Что показывает sequence-диаграмма?**
A: Обмен сообщениями между участниками во времени (сверху вниз).

**Q: include vs extend (Use Case)?**
A: include — обязательное включение. extend — опциональное расширение.

**Q: Агрегация vs композиция?**
A: Агрегация — часть живёт отдельно (пустой ромб). Композиция — часть не существует без целого (закрашенный ромб).

**Q: Уровни C4?**
A: Context → Container → Component → Code.

**Q: Как реализовать M:N?**
A: Через связующую таблицу с двумя внешними ключами.

## SQL и БД

**Q: Порядок выполнения SQL?**
A: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.

**Q: WHERE vs HAVING?**
A: WHERE — строки до группировки. HAVING — группы после, с агрегатами.

**Q: INNER vs LEFT JOIN?**
A: INNER — только совпадения. LEFT — все из левой + совпадения справа (NULL если нет).

**Q: Нормальные формы?**
A: 1НФ — атомарность. 2НФ — нет частичной зависимости от части ключа. 3НФ — нет транзитивных зависимостей.

**Q: Что такое индекс?**
A: Структура (B-tree) для ускорения чтения. Замедляет запись, занимает место.

**Q: ACID?**
A: Atomicity, Consistency, Isolation, Durability.

**Q: Уровни изоляции?**
A: Read Uncommitted → Read Committed → Repeatable Read → Serializable.

**Q: Аномалии транзакций?**
A: Грязное чтение, неповторяемое чтение, фантомы.

**Q: CAP-теорема?**
A: Из Consistency/Availability/Partition tolerance при разрыве сети выбираешь C или A.

**Q: SQL vs NoSQL?**
A: SQL — схема, связи, ACID, вертикальное масштабирование. NoSQL — гибкость, горизонтальное, BASE.

**Q: RANK vs DENSE_RANK vs ROW_NUMBER?**
A: RANK — пропускает номера при равных. DENSE_RANK — не пропускает. ROW_NUMBER — уникальный номер.

## API и интеграции

**Q: HTTP-методы и идемпотентность?**
A: GET/PUT/DELETE идемпотентны, POST — нет, PATCH — зависит.

**Q: 401 vs 403?**
A: 401 — не аутентифицирован. 403 — нет прав.

**Q: Что значат коды 200/201/400/404/500?**
A: 200 OK, 201 Created, 400 Bad Request, 404 Not Found, 500 Server Error.

**Q: Идемпотентность — что и зачем?**
A: Повтор запроса не меняет результат. Защита от дублей при retry (Idempotency-Key для POST).

**Q: REST vs SOAP?**
A: REST — JSON, гибкий, HTTP. SOAP — XML, строгий контракт WSDL, enterprise/банки.

**Q: REST принципы?**
A: Клиент-сервер, stateless, кэшируемость, единый интерфейс, ресурсы по URI.

**Q: Синхрон vs асинхрон?**
A: Синхрон — ждём ответ (REST). Асинхрон — отправил и не ждём (очередь), развязка, устойчивость к пикам.

**Q: gRPC — что и когда?**
A: Бинарный (Protobuf) поверх HTTP/2, быстрый — для межсервисного общения.

**Q: OpenAPI/Swagger?**
A: Стандарт описания REST API (YAML/JSON) → документация, генерация клиентов.

## Брокеры

**Q: Зачем брокер сообщений?**
A: Развязка сервисов, асинхрон, устойчивость к пикам, надёжность доставки.

**Q: Kafka — гарантия порядка?**
A: Только внутри партиции. Один ключ → одна партиция → порядок.

**Q: Kafka vs RabbitMQ?**
A: Kafka — лог событий, хранит, перечитываемо. RabbitMQ — очередь, гибкая маршрутизация, удаляет после ack.

**Q: Гарантии доставки?**
A: At most once, at least once, exactly once. Чаще at-least-once + идемпотентность.

**Q: DLQ?**
A: Dead Letter Queue — очередь для необработанных сообщений.

**Q: Outbox-паттерн?**
A: Атомарно пишем данные + событие в БД, отдельный процесс публикует в брокер. Решает «двойную запись».

**Q: Saga?**
A: Распределённая транзакция как цепочка локальных + компенсации при сбое. Хореография/оркестрация.

## Архитектура

**Q: Монолит vs микросервисы?**
A: Монолит — одно приложение, проще. Микросервисы — независимый деплой/масштаб, сложнее (сеть, согласованность).

**Q: API Gateway?**
A: Единая точка входа: маршрутизация, аутентификация, rate limiting, агрегация.

**Q: Горизонтальное vs вертикальное масштабирование?**
A: Вертикальное — мощнее сервер. Горизонтальное — больше серверов.

**Q: Репликация vs шардирование?**
A: Репликация — копии (масштаб чтения, доступность). Шардирование — разбиение по ключу (масштаб записи/объёма).

**Q: Circuit Breaker?**
A: Предохранитель: при серии ошибок отсекает вызовы, даёт сервису восстановиться.

**Q: CQRS?**
A: Разделение моделей чтения и записи.

## Безопасность

**Q: Аутентификация vs авторизация?**
A: Аутентификация — кто ты. Авторизация — что можно.

**Q: JWT?**
A: Stateless токен: Header.Payload.Signature. Payload подписан (не шифрован).

**Q: OAuth 2.0?**
A: Делегированная авторизация без передачи пароля (Authorization Code flow). OIDC — аутентификация поверх.

**Q: access vs refresh token?**
A: Access — короткий, для API. Refresh — длинный, для обновления access.

**Q: RBAC vs ABAC?**
A: RBAC — по ролям. ABAC — по атрибутам.

**Q: JSON vs XML?**
A: JSON — компактный, типы, REST. XML — многословный, схема XSD, SOAP.

## NFR

**Q: latency vs throughput?**
A: Latency — время одного запроса. Throughput — запросов в секунду.

**Q: Что такое p95/p99?**
A: Перцентиль: 95% запросов быстрее значения. Показывает «хвосты».

**Q: 99,9% доступности — сколько простоя?**
A: ~8,8 часов в год.

**Q: SLA/SLO/SLI?**
A: SLI — метрика, SLO — цель, SLA — соглашение со штрафами.

**Q: RTO vs RPO?**
A: RTO — время восстановления. RPO — допустимая потеря данных.

## Банки

**Q: Что такое идемпотентность в платеже?**
A: Повтор запроса не спишет деньги дважды (ключ идемпотентности).

**Q: СБП?**
A: Система быстрых платежей ЦБ — мгновенные переводы по телефону между банками.

**Q: KYC/AML?**
A: KYC — идентификация клиента. AML — противодействие отмыванию (115-ФЗ).

**Q: Эмитент vs эквайер?**
A: Эмитент выпустил карту. Эквайер обслуживает приём карт у мерчанта.

**Q: 3-D Secure?**
A: Доп. подтверждение онлайн-оплаты (SMS/push), снижает фрод.

**Q: Какой выбор по CAP для денег?**
A: CP — согласованность важнее доступности; RPO≈0.

**Q: Регуляторика РФ?**
A: 152-ФЗ (ПДн), 115-ФЗ (AML), 161-ФЗ (НПС), PCI DSS (карты).
