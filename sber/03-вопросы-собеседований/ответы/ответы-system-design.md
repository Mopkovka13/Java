# System Design — подробный разбор (для первого изучения)

Каждый вопрос: **простыми словами → подробнее → пример → зачем**. Список вопросов — в [system-design.md](../system-design.md).

> **Главная идея.** System design — это «как собрать систему из кубиков» (сервисы, базы, кеши, очереди) так, чтобы она выдерживала нагрузку и не падала. На собесе проверяют не «правильный ответ» (его нет), а **ход мыслей**: уточняешь ли требования, обосновываешь ли выбор, видишь ли узкие места.

Файл из двух частей: **концептуальные вопросы** (их задают и на обычной техсекции) и **скелеты решений** типовых задач дизайн-секции.

**Базовый набор «кубиков», из которых собирают почти любую систему:**
```
                          ┌──────────┐
  Клиент ──► [CDN] ──► [Load Balancer] ──► [API Gateway]
                                               │
                 ┌─────────────────────────────┼─────────────────────────┐
                 ▼                             ▼                          ▼
           [Сервис A] ◄──► [Кэш Redis]    [Сервис B]                 [Сервис C]
                 │                             │                          │
                 ▼                             ▼                          ▼
          [БД + реплики]               [Очередь Kafka] ──► воркеры   [внешние API]
                 │                             │
            (шардинг при росте)        (асинхронные эффекты)
```
Дальше каждый вопрос — про отдельный кубик или их связку.

## Часть 1. Концептуальные вопросы

### 1. Вертикальное vs горизонтальное масштабирование

**Простыми словами.**
- **Вертикальное** — взять сервер помощнее (больше CPU/RAM). Просто, но есть потолок, и это одна точка отказа.
- **Горизонтальное** — поставить много обычных серверов. Масштабируется почти безгранично, но требует, чтобы сервисы были **stateless** (не хранили состояние в себе), плюс нужен балансировщик.

**Аналогия.** Вертикальное — нанять одного супер-работника. Горизонтальное — нанять много обычных и распределять задачи между ними.

**Ключевой приём.** Бэкенд делаем stateless (состояние — в БД/Redis), и тогда можем запускать сколько угодно одинаковых копий за балансировщиком.

**Зачем.** Спросят «как масштабировать сервис» → сделать stateless и добавить реплики (горизонтально).

---

### 2. Как балансировщик распределяет нагрузку

**Простыми словами.** Балансировщик — «распределитель» запросов между копиями сервиса. Способы: по кругу (round-robin), на наименее загруженный (least connections), по клиенту (sticky — один клиент всегда на тот же сервер).

Он же делает **health checks** — проверяет, живы ли серверы, и убирает мёртвые из ротации.

**Аналогия.** Администратор в банке, направляющий клиентов к свободным окошкам.

**Зачем.** Базовый кубик горизонтального масштабирования. В Kubernetes это Service/Ingress.

---

### 3. Репликация БД: sync vs async, replication lag

**Простыми словами.** Репликация — копии базы на других серверах (для надёжности и масштабирования чтения).
- **Синхронная** — основная база ждёт подтверждения от копии перед коммитом. Ничего не потеряется, но медленнее.
- **Асинхронная** — коммитит сразу, копия догоняет потом. Быстро, но при падении основной можно потерять «хвост», а с реплики читать слегка устаревшее.

**Replication lag** — отставание копии от оригинала.

**Ловушка read-after-write.** Записал данные → сразу читаешь с реплики → её ещё не догнала → видишь старое. Решение: своё свежее читать с основной базы, а аналитику/отчёты — с реплик.

**Зачем.** Спросят «почему пользователь не видит то, что только что сохранил» → replication lag.

---

### 4. Шардирование: выбор ключа и проблемы

**Простыми словами.** Шардирование — разрезать данные по разным серверам, когда они не влезают в один. Главное — **выбрать ключ**, по которому режем. Хороший ключ: равномерно распределяет данные и собирает связанные данные вместе (для банка — `client_id`: все операции клиента на одном шарде).

**Проблемы:**
- **горячий шард** — если по одному ключу данных намного больше (перекос);
- **запросы между шардами** — медленно и сложно;
- **решардинг** — больно перераспределять при росте.

**Зачем.** Шардируй **только** когда реплик и мощного сервера уже не хватает. Спросят про выбор ключа → равномерность + паттерн доступа.

---

### 5. Уровни кеширования и проблемы кеша

**Простыми словами.** Кеш можно ставить на разных уровнях: браузер/CDN → API Gateway → локальный кеш в приложении (Caffeine) → общий кеш (Redis) → кеш самой БД. Чем ближе к пользователю — тем быстрее.

**Три главные проблемы:**
- **инвалидация** — как не отдавать устаревшее (TTL + удаление ключа при записи; сначала пишем в БД, потом сбрасываем кеш);
- **stampede (давка)** — ключ протух, и толпа разом ломится в БД (решают разбросом TTL и блокировкой на пересчёт);
- **несогласованность** между копиями приложения (короткий TTL локального кеша).

**Зачем.** «Самая сложная вещь в программировании — инвалидация кеша». Знай TTL + порядок «БД → потом кеш».

---

### 6. Зачем очередь (Kafka) в архитектуре

**Простыми словами.** Очередь между сервисами даёт:
- **развязку по времени** — получатель может временно лежать, события дождутся;
- **сглаживание пиков** — очередь работает буфером (приняли быстро, обрабатываем в своём темпе);
- **fan-out** — одно событие читают несколько потребителей;
- **надёжность** — повторы при сбоях.

**Цена:** результат не сразу (eventual consistency), возможны дубли (нужна идемпотентность), сложнее отслеживать поток.

**Аналогия.** Почтовый ящик: отправитель бросил письмо и ушёл, получатель заберёт когда сможет.

**Зачем.** Спросят «зачем тут Kafka» → развязка + пики + надёжность. См. [kafka-микросервисы](ответы-kafka-микросервисы.md).

---

### 7. Strong vs eventual consistency — как выбрать

**Простыми словами.**
- **Strong (строгая)** — все сразу видят актуальные данные. Нужна для денег: остаток на счёте, лимиты. Цена — медленнее и хуже доступность.
- **Eventual (в конечном счёте)** — данные «сойдутся потом», на секунды позже. Ок для лент, уведомлений, аналитики, поиска.

**Главное.** В одной системе сочетают: баланс — строго согласован в PostgreSQL; история операций в поисковом индексе — может отставать (eventual).

**Аналогия.** Баланс на счёте — должен быть точным сейчас. Лайки под постом — пусть обновятся через пару секунд, ничего страшного.

**Зачем.** Спросят «где нужна strong, где eventual» → деньги строго, всё остальное по возможности eventual (дешевле).

---

### 8. Отказоустойчивость вызовов между сервисами

**Простыми словами.** Чтобы один упавший сервис не уронил всех, применяют набор приёмов:
- **таймауты** — не ждать вечно (и меньше, чем ждёт твой вызывающий);
- **ретраи с backoff** — повтор с нарастающей паузой (только для идемпотентных операций!);
- **circuit breaker** — «предохранитель», быстрый отказ при серии ошибок;
- **fallback** — запасной ответ (отдать из кеша, урезанный результат);
- **rate limiting** — ограничение входящего потока.

**Зачем.** Спросят «сервис-сосед лёг, что делаешь» → таймаут + circuit breaker + fallback. См. [kafka-микросервисы](ответы-kafka-микросервисы.md) вопрос 12.

---

### 9. SLA / SLO / SLI и «девятки»

**Простыми словами.**
- **SLI** — измеряемый показатель (доля успешных запросов, p99 времени ответа);
- **SLO** — цель по этому показателю («99,9% успешных за месяц»);
- **SLA** — договор с клиентом + штрафы за нарушение.

**«Девятки» = сколько простоя в год:**
| Доступность | Простой/год |
|---|---|
| 99,9% (три девятки) | ~8,8 часа |
| 99,99% (четыре) | ~52 минуты |
| 99,999% (пять) | ~5 минут |

Каждая девятка дороже: резервирование, авто-переключение, деплой без простоя.

**Зачем.** Спросят «что значит четыре девятки» → ~52 минуты простоя в год.

---

### 10. Как спроектировать rate limiter (ограничитель запросов)

**Простыми словами.** Rate limiter не даёт одному клиенту завалить систему. Самый ходовой алгоритм — **token bucket («ведро токенов»)**: у клиента есть «ведро» с токенами, каждый запрос тратит токен, ведро пополняется со временем. Закончились токены — ответ **429 Too Many Requests** + заголовок `Retry-After`.

В распределённой системе счётчики хранят в Redis (атомарно).

**Аналогия.** Турникет, выдающий жетоны: жетоны кончились — подожди, пока подкинут новые.

**Зачем.** Спросят «как ограничить число запросов» → token bucket + 429 + счётчики в Redis.

---

### 11. Оценка нагрузки (back-of-envelope)

**Простыми словами.** «Прикидка на салфетке» — быстрый расчёт порядков чисел, чтобы понять масштаб. Точность не нужна, нужны порядки и проговорённые вслух допущения.

**Пример расчёта:**
```
10 млн пользователей в день × 10 запросов = 100 млн запросов/день
100 млн / 86400 сек ≈ 1200 запросов/сек (средние)
пик ×3–5 ≈ 5000 запросов/сек
хранение: 100 млн × 1 КБ ≈ 100 ГБ/день ≈ 36 ТБ/год
```
**Выводы из цифр:** нужен ли шардинг, сколько инстансов (грубо 1 инстанс ≈ 500–1000 лёгких RPS), где обязателен кеш.

**Зачем.** Сильный сигнал на собесе: ты выводишь архитектуру **из цифр**, а не наугад. Проговаривай допущения вслух.

---

### 12. Наблюдаемость (observability)

**Простыми словами.** Чтобы понимать, что происходит в распределённой системе, нужны три вещи:
- **метрики** (Prometheus) — числа: сколько запросов, ошибок, как быстро; по ним алерты;
- **логи** — структурированные, в одном месте, с trace id (чтобы связать строки одного запроса);
- **трейсинг** (OpenTelemetry) — путь запроса через все сервисы: видно, где именно затормозило.

**Аналогия.** Метрики — приборная панель машины; логи — бортовой журнал; трейсинг — GPS-трек всей поездки.

**Зачем.** Без этого инцидент разбираешь гаданием. Спросят «как поймёшь, где тормозит» → метрики + логи с trace id + трейсинг.

## Часть 2. Скелеты решений типовых задач

> Это «рыба» ответа. На собесе сначала **уточни требования**, потом разворачивай по шагам: требования → оценка нагрузки → модель данных → API → схема → узкие места.

### 13. Система переводов / платежей

**Требования:** перевод A→B, нельзя потерять и нельзя задвоить деньги; ~1–5к RPS; нужен аудит.

**Каркас:**
- **Хранилище:** PostgreSQL. Таблица операций (ledger, только добавление) + таблица счетов.
- **Перевод = одна транзакция:** списать + зачислить + записать операцию. Блокировка строк счетов **в одном порядке по id** (против deadlock) или оптимистичная блокировка + повтор.
- **Идемпотентность:** клиентский ключ + уникальный индекс; повтор возвращает сохранённый результат (не списывает снова).
- **Внешние эффекты** (уведомления, антифрод): через **transactional outbox → Kafka**, не прямо из транзакции.
- **Статусы:** PENDING → COMPLETED/FAILED; межбанк — Saga с компенсациями.
- **Упомяни проактивно:** аудит неизменяем, сверка (реконсиляция) с контрагентами, шардирование ledger по client_id при росте.

**Схема:**
```
Клиент ──(Idempotency-Key)──► [API Gateway] ──► [Payment Service]
                                                       │
                              ┌─── одна транзакция БД ──┴────────────┐
                              │ списать со счёта A                   │
                              │ зачислить на счёт B                  │
                              │ INSERT в ledger (append-only)        │
                              │ INSERT в outbox ("TransferDone")     │
                              └──────────────────────────────────────┘
                                                       │ commit
                                                       ▼
                                  [outbox → Kafka] ──► [Антифрод][Уведомления][Вебхуки]
```

**Зачем.** Главная банковская задача. Связывает всё: транзакции, идемпотентность, outbox, saga.

---

### 14. Система уведомлений (push / sms / email)

**Каркас:**
- **Вход:** события из Kafka.
- **Оркестратор:** применяет правила (какой канал, шаблон, предпочтения пользователя, «тихие часы») → кладёт в очередь на каждый канал → воркеры-отправщики с ограничением скорости под провайдеров.
- **Надёжность:** повторы с backoff, DLQ, идемпотентность по event id (не отправить дважды), приоритеты (код подтверждения важнее рекламы).
- **Статусы доставки** — обратные колбэки провайдеров.

**Зачем.** Частая задача. Покажи идемпотентность (не слать дубли) и приоритетные очереди.

---

### 15. Сокращатель ссылок (short URL)

**Каркас:**
- **Оценка:** запись ~100/с, чтение ~10к/с — система «читающая» (read-heavy 100:1).
- **Генерация кода:** base62 от счётчика (диапазоны раздаём инстансам) или случайный код с проверкой коллизий.
- **Хранение:** простая модель «ключ→значение» (PostgreSQL, при росте — Cassandra).
- **Чтение:** кеш Redis для горячих ссылок, ответ — редирект 301/302.
- **Аналитика кликов:** события в Kafka, считаем офлайн, чтобы не тормозить редирект.

**Зачем.** Классическая «разминочная» задача. Покажи, что под read-heavy ставишь кеш.

---

### 16. Лента операций / выписка

**Каркас:**
- **Паттерн:** много чтений, данные не меняются после записи.
- **Пагинация:** cursor по (timestamp, id) с составным индексом (не offset — он медленный вглубь).
- **Горячее/холодное:** свежие 3 месяца — основная таблица/кеш; старое — партиции по месяцам (совсем старое — в архив/объектное хранилище).
- **Агрегаты** (обороты за месяц): предрассчитанные, обновляются событиями.
- **Поиск по выписке:** отдельный индекс (Elasticsearch), наполняется через Kafka (отставание допустимо).

**Зачем.** Показывает работу с большими read-heavy данными: cursor-пагинация, партиции, отдельный поиск.

---

### 17. Как вести себя на дизайн-секции (чек-лист)

1. **5–10 минут на требования** и уточняющие вопросы — не прыгай сразу в решение.
2. **Цифры вслух** (RPS, объёмы) → из них выводи архитектуру.
3. **Сначала простая схема end-to-end**, потом углубляйся в 1–2 компонента (по выбору интервьюера).
4. **Каждый выбор — с trade-off:** «беру Kafka, потому что X; цена — Y».
5. **Сам назови узкие места и точки отказа** — не жди вопроса.
6. **Банковский контекст** (идемпотентность, аудит, согласованность денег) упоминай проактивно — в Сбере это ценят.

---

## Как отвечать на собесе по System Design

1. **Структура важнее деталей:** требования → нагрузка → данные → API → схема → узкие места. Иди по шагам вслух.
2. **Нет «правильного» ответа** — есть обоснованные компромиссы. Всегда говори «почему» и «какой ценой».
3. **Переиспользуй кубики** из части 1: балансировщик, реплики, шарды, кеш, очередь, circuit breaker.
4. **Для банка** держи в голове: деньги = строгая согласованность + идемпотентность + аудит.
