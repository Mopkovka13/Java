# Kafka, микросервисы, инфраструктура — подробный разбор (для первого изучения)

Каждый вопрос: **простыми словами → подробнее → пример → зачем**. Список вопросов — в [kafka-микросервисы.md](../kafka-микросервисы.md).

> **Главная идея.** Когда сервисов много, они должны как-то общаться. Можно напрямую (REST — «позвонил и ждёшь ответ»), а можно через Kafka («оставил сообщение, ушёл по делам»). Эта тема — про то, как организовать такое общение надёжно: чтобы ничего не потерялось и не задвоилось.

---

## Apache Kafka

### 1. Что такое Kafka (в двух словах)

**Простыми словами.** Kafka — это «общий журнал событий». Сервисы пишут в него сообщения, другие сервисы их читают. Главное отличие от обычной очереди: Kafka **хранит** сообщения (не удаляет после прочтения), и их можно перечитать.

**Аналогия.** Лента новостей: автор опубликовал пост (сообщение), он остаётся в ленте, любой читатель может прочитать его в своём темпе и даже перечитать.

**Ключевые слова:**
- **топик** — категория сообщений (например, «платежи»);
- **партиция** — топик разбит на части для параллельности; внутри партиции сообщения строго упорядочены;
- **оффсет** — порядковый номер сообщения в партиции; каждый читатель помнит, до какого места дочитал.

**Схема:**
```
Topic "payments"
  Partition 0: [m0][m1][m2][m3][m4]...      ──── offset растёт ───►
  Partition 1: [m0][m1][m2]...
  Partition 2: [m0][m1][m2][m3]...
                ▲ продюсер пишет в конец        ▲ консьюмер читает со своего offset
  Сообщения НЕ удаляются после чтения (retention по времени/размеру → можно перечитать)
```

**🔍 Если копнут глубже:**
- Каждая партиция **реплицируется** на несколько брокеров: один — **лидер** (принимает запись), остальные — **фолловеры** (догоняют). **ISR** (in-sync replicas) — реплики, успевающие за лидером; `acks=all` ждёт подтверждения именно от ISR.
- При падении лидера новый выбирается **из ISR** — поэтому `min.insync.replicas=2` защищает от потери данных.
- **Retention** настраивается (`retention.ms`/`retention.bytes`); есть и **log compaction** — режим, где Kafka хранит последнее значение по каждому ключу (удобно для «снимка состояния»).
- Партиция — единица параллелизма и порядка: больше партиций = больше параллельных читателей, но и больше накладных расходов.

**Зачем.** Базовый вопрос. Запомни: Kafka = хранимый лог событий, читатели сами отслеживают позицию.

### 2. Как гарантировать порядок сообщений

**Простыми словами.** Kafka гарантирует порядок **только внутри одной партиции**, не по всему топику. Чтобы связанные события (например, по одному счёту) шли строго по порядку, их отправляют с **одинаковым ключом** (id счёта) — тогда они попадут в одну партицию.

**Аналогия.** Несколько касс в магазине (партиции). Если хочешь, чтобы твои покупки обработали по порядку, — иди всегда в одну кассу (один ключ).

**Подвох.** Если потом увеличить число партиций, распределение ключей изменится, и порядок «на стыке» может сломаться — планируй число партиций заранее.

**Зачем.** Частый вопрос. Запомни: порядок только в партиции; для порядка по сущности — один ключ.

### 3. Consumer group и ребалансировка

**Простыми словами.** Consumer group — «команда читателей», которые делят между собой партиции, чтобы читать параллельно. Правило: **одну партицию читает максимум один читатель из группы**. Поэтому читателей больше, чем партиций — лишние простаивают.

Когда читатель добавился/упал — происходит **ребалансировка**: партиции перераспределяются.

**Аналогия.** Бригада грузчиков делит вагоны: один грузчик — один вагон. Грузчиков больше вагонов — кто-то стоит без дела.

**Схема:**
```
Topic (3 партиции)        Consumer Group "billing"
  Partition 0 ──────────► Consumer A
  Partition 1 ──────────► Consumer B
  Partition 2 ──────────► Consumer C
                          Consumer D  ← простаивает (партиций не осталось)

Другая группа "analytics" читает ТОТ ЖЕ топик независимо, со своими offset.
```

**Зачем.** Объясняет, как масштабировать чтение. Запомни: число партиций = потолок параллельности группы.

### 4. Гарантии доставки (at-most / at-least / exactly-once)

**Простыми словами.** Сколько раз сообщение точно обработается:
- **at-most-once** (максимум раз) — можем **потерять** при сбое;
- **at-least-once** (минимум раз) — не потеряем, но возможны **дубли** (стандарт на практике);
- **exactly-once** (ровно раз) — идеал, но сложно и есть ограничения.

**На практике** для работы с внешней БД используют **at-least-once + идемпотентный консьюмер** (умеющий безопасно обработать дубль). См. вопрос 6.

**Аналогия.** at-least-once — курьер перезвонит, если не дозвонился: точно доставит, но мог звонить дважды.

**🔍 Если копнут глубже (как Kafka делает exactly-once):**
- **Идемпотентный продюсер** (`enable.idempotence=true`): брокер помечает сообщения парой (PID продюсера + порядковый номер) и **отбрасывает дубли** при ретраях — защита от двойной записи на стороне продюсера.
- **Транзакции Kafka:** можно атомарно записать сообщения **и** закоммитить offset’ы потребления — это даёт exactly-once для паттерна **read-process-write внутри Kafka** (читаем из топика, пишем в топик).
- Консьюмер при этом должен читать с `isolation.level=read_committed`, чтобы не видеть незакоммиченные сообщения.
- **Важная оговорка:** exactly-once работает **внутри Kafka**. Как только в цепочке внешняя БД или сторонний API — гарантия не распространяется, и всё равно нужен идемпотентный консьюмер (вопрос 6) или Outbox (вопрос 11).

**Зачем.** Топ-вопрос. Запомни связку: at-least-once + идемпотентность.

### 5. Параметр acks

**Простыми словами.** `acks` — «сколько подтверждений ждать, что сообщение записалось»:
- **acks=0** — не ждать вообще (быстро, но можем потерять);
- **acks=1** — ждать подтверждения от лидера (можем потерять, если лидер упадёт);
- **acks=all** — ждать подтверждения от всех синхронных реплик (надёжно, **стандарт для денег**).

**Зачем.** Спросят «как не потерять сообщение» → `acks=all`.

### 6. Как сделать консьюмер идемпотентным

**Простыми словами.** Идемпотентный консьюмер — тот, что **безопасно переживает дубль**: повторная обработка того же сообщения не приводит к двойному эффекту. Способ: запоминать id уже обработанных сообщений и пропускать повторы.

```java
@KafkaListener(topics = "payments")
@Transactional
public void handle(PaymentEvent e) {
    try {
        processedRepo.save(new ProcessedEvent(e.eventId())); // уникальный id
    } catch (DataIntegrityViolationException dup) {
        return;                          // дубль — уже обрабатывали, пропускаем
    }
    accountService.apply(e);             // эффект в ТОЙ ЖЕ транзакции БД
}
```

**Аналогия.** Список «кому уже выдал зарплату»: пришёл человек повторно — сверился со списком, второй раз не выдал.

**Зачем.** Это и есть практическое решение проблемы дублей из вопроса 4. Очень важно для банков.

### 7. Зачем DLQ (Dead Letter Queue)

**Простыми словами.** Бывает «ядовитое» сообщение — битый формат или ошибка, которую никогда не получится обработать. Если его бесконечно пытаться обработать, оно **заблокирует всю партицию** (за ним очередь стоит). Решение: после N попыток отправить его в отдельный топик-«отстойник» (DLQ) и ехать дальше, а инженеры разберут отдельно.

**Аналогия.** На конвейере застряла бракованная деталь — её снимают в отдельный ящик, чтобы не останавливать весь конвейер.

**Зачем.** Спросят «что делать с необрабатываемым сообщением» → DLQ + алерт.

---

### 8. Kafka vs RabbitMQ

**Простыми словами.**
- **Kafka** — «хранимый лог», сообщения остаются, можно перечитать, огромная пропускная способность. Для потоков событий, интеграции сервисов.
- **RabbitMQ** — «умная очередь задач», сообщение удаляется после обработки, гибкая маршрутизация. Для задач/команд.

| | Kafka | RabbitMQ |
|---|---|---|
| Модель | хранимый лог | очередь |
| После прочтения | остаётся | удаляется |
| Сила | поток событий, объёмы | маршрутизация задач |

**Зачем.** Частое сравнение. Запомни: Kafka хранит и перечитывает, Rabbit удаляет после ack.

## Паттерны микросервисов

### 9. Синхронное vs асинхронное общение

**Простыми словами.**
- **Синхронно (REST/gRPC)** — «позвонил и ждёшь ответ». Просто, но если вызываемый сервис упал — падает вся цепочка, а задержки складываются.
- **Асинхронно (Kafka)** — «отправил сообщение и пошёл дальше». Сервисы развязаны, переживают пики и сбои; цена — результат не сразу (eventual consistency) и сложнее отлаживать.

**Правило.** Нужны данные **прямо сейчас** → синхронно. Сообщаешь **о факте/событии** («заказ создан») → асинхронно.

**Зачем.** Спросят «когда REST, когда очередь» → используй это правило.

---

### 10. Saga — распределённая транзакция

**Простыми словами.** В микросервисах нет одной общей транзакции на всех. Saga — это цепочка локальных транзакций в разных сервисах; если шаг не удался — выполняются **компенсации** (отменить бронь, вернуть деньги).

**Два вида:**
- **Хореография** — сервисы реагируют на события друг друга, без начальника. Просто начать, сложно отследить.
- **Оркестрация** — есть «дирижёр» (оркестратор), который командует шагами. Виден весь процесс. В банках чаще оркестрация — важны контроль и аудит.

**Аналогия.** Заказ тура: бронь отеля → билеты → трансфер. Если билетов нет — отменяем (компенсируем) бронь отеля.

**Зачем.** Главный паттерн согласованности в микросервисах. Знай про компенсации.

### 11. Transactional Outbox

**Простыми словами.** Проблема: надо **и** записать в БД, **и** отправить событие в Kafka. Сделать это атомарно нельзя — если упасть между двумя действиями, данные и событие разойдутся.

**Решение.** В **одной** транзакции БД пишем и бизнес-данные, и событие в специальную таблицу `outbox`. Отдельный процесс потом читает `outbox` и отправляет в Kafka. Гарантия: событие уйдёт тогда и только тогда, когда транзакция закоммичена.

```java
@Transactional
public void createPayment(Payment p) {
    paymentRepo.save(p);                                   // бизнес-данные
    outboxRepo.save(OutboxEvent.of("PaymentCreated", p));  // событие — та же транзакция
}
// ❌ нельзя kafkaTemplate.send() прямо тут: упадём после коммита БД, но до отправки → событие потеряно
// ✅ отдельный поллер читает outbox и публикует в Kafka
```

**Схема:**
```
┌──── одна транзакция БД ────────────┐
│  INSERT payment       (бизнес-данные)│
│  INSERT outbox_event ("PaymentCreated")│
└────────────────────────────────────┘
            │ commit
            ▼
   [Поллер или Debezium CDC] читает outbox
            │
            ▼
         Kafka ──► консьюмеры (идемпотентные)
            │
            ▼
   UPDATE outbox SET sent = true
```

**Аналогия.** Вместо «сделал дело и сразу побежал звонить» — записал задачу в блокнот в той же операции; отдельный помощник потом обзванивает по блокноту. Запись в блокнот не потеряется.

**Зачем.** Очень важный паттерн (в этом проекте даже есть `outbox-starter`). Решает «двойную запись».

### 12. Circuit Breaker — состояния

**Простыми словами.** «Предохранитель»: если вызываемый сервис постоянно падает, нет смысла долбить его — лучше быстро отдавать ошибку/заглушку и дать ему восстановиться.

**Три состояния:**
- **Closed** (замкнут) — пропускаем вызовы, считаем ошибки;
- **Open** (разомкнут) — превышен порог ошибок, мгновенно отказываем без вызова;
- **Half-Open** (полуоткрыт) — через время пробуем пару запросов: успех → Closed, провал → снова Open.

**Схема (состояния):**
```
         ошибок < порога                 порог ошибок превышен
  ┌──────────────────┐ ──────────────────────────────────────► ┌─────────────┐
  │      CLOSED       │                                          │    OPEN     │
  │  (пропускаем,     │ ◄──────────────────────────────────────  │ (мгновенный │
  │   считаем ошибки) │          проба успешна                    │  отказ)     │
  └──────────────────┘                                          └──────┬──────┘
          ▲                    ┌──────────────┐                        │ прошёл таймаут
          └────────────────────│  HALF-OPEN   │◄───────────────────────┘
             проба успешна     │ (пробный     │
                               │  запрос)     │── проба провалилась ──► снова OPEN
                               └──────────────┘
```

**Аналогия.** Электрический предохранитель: при перегрузке вырубается, чтобы не сгорела проводка.

**Зачем.** Защита от каскадных падений. Сочетают с таймаутами и retry. Инструмент — Resilience4j.

### 13. Зачем idempotency key в платёжном API

**Простыми словами.** Клиент отправил `POST /payments`, не дождался ответа (таймаут) и **повторил**. Без защиты деньги спишутся дважды. Решение: клиент генерирует **уникальный ключ операции**, сервер запоминает «ключ → результат». Повтор с тем же ключом возвращает прежний результат, а не выполняет операцию снова.

**Аналогия.** Номерок в очереди: подошёл повторно с тем же номерком — тебе отдают уже готовый результат, а не обслуживают заново.

**Зачем.** Обязательный паттерн в банке. Связан с идемпотентностью консьюмера (вопрос 6) и retry.

## REST

### 14. Идемпотентные методы и коды ошибок

**Простыми словами.** Идемпотентный = повтор не меняет результат сверх первого раза.
- Идемпотентны: **GET, PUT, DELETE**. **POST — нет** (повтор создаёт ещё один объект).

**Коды:**
- **400** — кривой запрос (синтаксис); **422** — формат верный, но не прошла бизнес-валидация;
- **401** — не залогинен; **403** — залогинен, но нет прав;
- **404** — нет ресурса; **409** — конфликт (дубль, устаревшая версия).

**Зачем.** Спрашивают постоянно. Запомни хотя бы 400/401/403/404/409/500.

---

### 15. Offset vs cursor пагинация

**Простыми словами.**
- **Offset** (`LIMIT 20 OFFSET 1000`) — «пропусти 1000, дай 20». Просто, но чем глубже — тем медленнее (БД читает и выбрасывает 1000 строк), и страницы «съезжают» при вставках.
- **Cursor/keyset** — «дай 20 после вот этой записи». Быстро и стабильно, но нельзя прыгнуть сразу на страницу 50.

**Зачем.** Для лент и выписок (банк) — cursor. Спросят «почему offset медленный на больших страницах».

## Docker / Kubernetes

### 16. Liveness vs readiness probe

**Простыми словами.** Kubernetes регулярно «проверяет здоровье» контейнера двумя проверками:
- **liveness** — «процесс вообще жив?» Провалилась → контейнер **перезапускают** (помогает при зависании).
- **readiness** — «готов принимать трафик?» Провалилась → под **убирают из балансировки**, но **не убивают** (например, ещё прогревается или временно нет БД).

**Важная ошибка.** Не клади проверку БД в liveness: если БД мигнула, Kubernetes начнёт бесконечно перезапускать поды (каскад). Зависимости — в readiness.

**Зачем.** Практический вопрос по эксплуатации. Запомни разницу: liveness рестартит, readiness убирает из трафика.

---

### 17. CPU throttling и JVM в контейнере

**Простыми словами.** Если контейнеру задан лимит CPU, и он его исчерпал в текущем «окне» — система **притормаживает** (throttling) процесс до следующего окна. Это даёт паузы и рост задержек.

**Память:** ставь `-Xmx` около 75% лимита памяти (остальное — на классы, стеки, нативную память), иначе контейнер убьют (OOMKilled, код 137) без диагностики.

**Зачем.** Все деплоят в Kubernetes — сильный практический ответ. Связано с Java Core вопрос 30.

---

### 18. Graceful shutdown в Kubernetes

**Простыми словами.** При остановке пода Kubernetes шлёт сигнал SIGTERM. Проблема: трафик может ещё идти, а приложение уже завершается → ошибки. Нужно завершаться **аккуратно**: дослать ответы на текущие запросы, корректно закрыть Kafka-консьюмеры и пулы.

**Как:** `server.shutdown=graceful` в Spring + небольшая пауза (preStop hook), чтобы под успел выйти из балансировки.

**Зачем.** Спросят «как остановить сервис без потери запросов» → graceful shutdown.

---

### 19. Service mesh (Istio/Envoy)

**Простыми словами.** Service mesh — это когда рядом с каждым сервисом ставят «сетевого помощника» (sidecar-прокси), который берёт на себя: шифрование между сервисами (mTLS), повторы, таймауты, circuit breaking, сбор метрик — **без изменения кода приложения**.

**Зачем.** В Сбере это основа платформы Platform V Synapse — упомяни на собесе, плюс в карму.

## CI/CD

### 20. Этапы CI/CD пайплайна

**Простыми словами.** CI/CD — автоматический конвейер от кода до прода:
1. **Build** — компиляция + юнит-тесты;
2. **Проверка качества** — статический анализ (SonarQube);
3. **Интеграционные тесты** (Testcontainers);
4. **Сборка и скан образа** (Docker);
5. **Деплой** на стейдж → автотесты → прод.

**Стратегии выкатки на прод:**
- **rolling** — постепенно заменяем старые поды новыми;
- **blue-green** — поднимаем полную новую среду и мгновенно переключаем;
- **canary** — пускаем малый % трафика на новую версию, смотрим метрики.

**Зачем.** Спросят «как доставляешь код в прод» и «чем canary отличается от blue-green».

## Как отвечать на собесе по Kafka/микросервисам

1. **Связывай проблему и решение:** дубли → идемпотентность; «двойная запись» → Outbox; распределённая транзакция → Saga; каскадные сбои → Circuit Breaker.
2. **Главная триада надёжности:** at-least-once + идемпотентный консьюмер + Outbox. Если расскажешь эту связку — сразу видно, что понимаешь.
3. **Sync vs async** — умей обосновать выбор.
4. **Инфраструктура** (Kubernetes, probes, JVM в контейнере) — большой плюс, многие аналитики/джуны этого не знают.
