# Базы данных и SQL — подробный разбор (для первого изучения)

Каждый вопрос: **простыми словами → подробнее → пример → зачем**. Список вопросов — в [базы-данных-sql.md](../базы-данных-sql.md).

> **Главная идея.** База — это таблицы (как листы Excel) со связями между ними. SQL — язык запросов к ним. Тебя проверяют на трёх вещах: умеешь ли писать запросы (JOIN, агрегаты, окна), понимаешь ли производительность (индексы) и надёжность (транзакции).

## SQL

### 1. Типы JOIN

**Простыми словами.** JOIN склеивает строки из двух таблиц по условию (обычно по ключу). Разница — что делать со строками без пары:
- **INNER** — только те, у кого есть пара в обеих таблицах;
- **LEFT** — все из левой таблицы + пары из правой (нет пары → NULL);
- **RIGHT** — зеркально (все из правой);
- **FULL OUTER** — все из обеих;
- **CROSS** — каждая с каждой (декартово произведение).

**Схема:**
```
  таблица A        таблица B
   ┌───┐            ┌───┐
   │ A │            │ B │
   └─┬─┘            └─┬─┘
     └──── A ∩ B ─────┘

 INNER  = только A ∩ B           (пересечение)
 LEFT   = все A + совпавшие из B  (нет пары → NULL)
 RIGHT  = все B + совпавшие из A
 FULL   = все строки A ∪ B
```

**Аналогия.** Два списка: «сотрудники» и «их машины». INNER — только сотрудники с машинами. LEFT — все сотрудники, у кого нет машины — пустое место.

**Главная ловушка (спрашивают часто!):** условие на правую таблицу в `WHERE` превращает `LEFT JOIN` обратно в `INNER` — потому что строки с NULL не проходят фильтр.
```sql
-- ❌ хотели «все клиенты + их оплаченные заказы», но потеряли клиентов без заказов:
SELECT c.name, o.id FROM client c
LEFT JOIN orders o ON o.client_id = c.id
WHERE o.status = 'PAID';        -- NULL не проходит фильтр → фактически INNER

-- ✅ условие по правой таблице — внутри ON, а не в WHERE:
SELECT c.name, o.id FROM client c
LEFT JOIN orders o ON o.client_id = c.id AND o.status = 'PAID';
```

**Зачем.** JOIN — основа SQL. Запомни картинку «INNER = пересечение, LEFT = всё слева» и ловушку с WHERE.

### 2. WHERE vs HAVING

**Простыми словами.** Оба фильтруют, но в разные моменты:
- **WHERE** — фильтрует **строки до** группировки (агрегаты `SUM`/`COUNT` тут недоступны);
- **HAVING** — фильтрует **группы после** группировки (тут можно `COUNT(*) > 5`).

```sql
SELECT client_id, SUM(amount) AS total
FROM orders
WHERE status = 'PAID'        -- сначала отсекли неоплаченные строки
GROUP BY client_id
HAVING SUM(amount) > 10000;  -- потом отсекли группы с маленькой суммой
```

**Зачем.** Частый вопрос. Запомни: фильтр по агрегату → только HAVING; обычный фильтр → WHERE (он дешевле, отсекает раньше).

### 3. Оконные функции vs GROUP BY

**Простыми словами.** `GROUP BY` **схлопывает** группу в одну строку. Оконная функция (`OVER`) считает то же самое (сумму, ранг), но **сохраняет все строки** — добавляет результат как ещё одну колонку.

**Аналогия.** GROUP BY: «средняя зарплата по отделам» — одна строка на отдел. Оконная: «каждый сотрудник + средняя по его отделу рядом» — все сотрудники на месте.

**Функции:** `ROW_NUMBER` (просто нумерация 1,2,3), `RANK` (с пропусками при равенстве: 1,1,3), `DENSE_RANK` (без пропусков: 1,1,2), `LAG/LEAD` (соседняя строка).

```sql
-- Топ-2 зарплаты в каждом отделе (строки сохранены!):
SELECT * FROM (
  SELECT e.*, DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rnk
  FROM employee e
) t WHERE rnk <= 2;

-- Насколько баланс изменился с прошлой операции клиента:
SELECT op.*,
       balance - LAG(balance) OVER (PARTITION BY client_id ORDER BY created) AS delta
FROM operations op;
```

**Зачем.** Топ-задача на собесе «top-N по группе». Запомни шаблон: подзапрос с `DENSE_RANK` + внешний `WHERE rnk <= N`.

### 4. UNION vs UNION ALL, EXISTS vs IN

**Простыми словами.**
- **UNION** склеивает результаты двух запросов и **убирает дубликаты** (дороже — нужна сортировка). **UNION ALL** — оставляет всё (быстрее).
- **EXISTS** проверяет «есть ли хоть одна строка» и останавливается на первой. **IN** сравнивает со списком значений.

**Опасная ловушка:** `NOT IN` с `NULL` в подзапросе вернёт **пустой результат** (из-за логики NULL). Используй `NOT EXISTS`.
```sql
-- ❌ если в orders.client_id есть хоть один NULL — результат ПУСТОЙ:
SELECT * FROM client WHERE id NOT IN (SELECT client_id FROM orders);

-- ✅ NOT EXISTS работает корректно:
SELECT * FROM client c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.client_id = c.id);
```

**Зачем.** `UNION ALL` если дубликаты не важны (быстрее). `NOT EXISTS` вместо `NOT IN` — чтобы не споткнуться о NULL.

## Индексы и производительность

### 5. Как устроен B-tree индекс и когда не работает

**Простыми словами.** Индекс — это как алфавитный указатель в конце книги: вместо листания всей книги (всех строк) ты сразу прыгаешь на нужную страницу. B-tree — отсортированное дерево, поиск за O(log n), хорош и для диапазонов (`BETWEEN`, `>`, `<`).

**Когда индекс НЕ срабатывает:**
- функция над колонкой: `WHERE lower(name) = 'ivan'` (нужен индекс по выражению);
- `LIKE '%abc'` — поиск с начала неизвестен (wildcard в начале);
- низкая селективность — если под условие попадает полтаблицы, дешевле прочитать всё подряд;
- разные типы данных в сравнении.

```sql
-- ❌ индекс по created не используется — функция «прячет» колонку:
WHERE date_trunc('day', created) = '2026-06-15'
-- ✅ переписать диапазоном — индекс работает:
WHERE created >= '2026-06-15' AND created < '2026-06-16'
```

**Схема (B-tree):**
```
                 [ 50 | 100 ]                  ← корень
                /     |       \
         [10|30]   [60|80]   [120|150]         ← внутренние узлы
         / | \      ...
   листья: отсортированные ключи + ссылки на строки,
   связаны в цепочку ◄──►  → быстрый поиск по диапазону (BETWEEN, >, <)
```

**Зачем.** Спросят «почему запрос медленный». Частый ответ — функция над колонкой убила индекс.

---

### 6. Составной индекс — правило порядка колонок

**Простыми словами.** Индекс по нескольким колонкам `(a, b)` работает «слева направо», как телефонный справочник (отсортирован сначала по фамилии, потом по имени). Он помогает искать по `a` и по `a + b`, но **не помогает** искать только по `b`.

**Правило:** колонки с равенством (`=`) ставь в начало, колонку с диапазоном (`>`, `<`) — в конец.

```sql
-- индекс (client_id, created)
WHERE client_id = 5 AND created > '2026-01-01'   -- ✅ работает идеально
WHERE created > '2026-01-01'                      -- ❌ только по второй колонке — не работает
```

**Зачем.** Тонкое, но частое место для middle. Запомни: «равенство в начало, диапазон в конец».

---

### 7. Специальные индексы PostgreSQL

**Простыми словами.** Кроме обычного B-tree есть специальные:
- **GIN** — для массивов, JSON (jsonb), полнотекстового поиска («найди слово в тексте»);
- **GiST** — для геометрии, диапазонов, поиска «ближайших»;
- **BRIN** — для огромных таблиц с естественным порядком (логи по датам) — крошечный, хранит min/max по блокам;
- **Partial** — индекс только по части строк (`WHERE active = true`) — меньше и быстрее;
- **Hash** — только для точного равенства.

**Зачем.** Достаточно знать, что для JSON/полнотекста есть GIN, а для «свежих логов по дате» — BRIN. Покажет кругозор.

---

### 8. Что смотреть в EXPLAIN ANALYZE

**Простыми словами.** `EXPLAIN ANALYZE` показывает «план запроса» — как именно БД его выполнит и сколько это стоит. На что смотреть:
- **Seq Scan** (полный перебор) на большой таблице с узким фильтром → не хватает индекса;
- большое расхождение «ожидалось строк / реально строк» → устаревшая статистика, сделать `ANALYZE`;
- самый «дорогой» узел плана — туда и копать.

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE client_id = 5;
-- видим "Seq Scan on orders" при миллионе строк → добавить индекс по client_id
```

**Зачем.** Практический инструмент диагностики. Спросят «как найдёшь, почему запрос тормозит» → EXPLAIN ANALYZE.

---

### 9. Цена индексов

**Простыми словами.** Индексы ускоряют **чтение**, но замедляют **запись**: при каждом INSERT/UPDATE/DELETE обновляются все индексы таблицы. Плюс они занимают место.

**Правило.** Создавай индексы под реальные запросы, а не «на всякий случай». Неиспользуемые индексы — чистый вред (тормозят запись, едят место).

**Зачем.** Покажет баланс. Спросят «можно ли навесить индексы на всё» → нет, запись подорожает.

## Транзакции

### 10. ACID

**Простыми словами.** Четыре гарантии надёжной транзакции:
- **Atomicity (атомарность)** — «всё или ничего»: при сбое всё откатывается. Перевод денег: либо списали и зачислили, либо ничего.
- **Consistency (согласованность)** — БД остаётся в корректном состоянии (соблюдены ограничения).
- **Isolation (изоляция)** — параллельные транзакции не видят «полуготовых» данных друг друга.
- **Durability (долговечность)** — после коммита данные не пропадут даже при выключении света.

**Зачем.** Базовый вопрос. Лучший пример атомарности — перевод денег.

---

### 11. Уровни изоляции и аномалии

**Простыми словами.** Чем сильнее изоляция, тем меньше «странностей» при параллельной работе, но тем медленнее. От слабого к сильному:

| Уровень | Что ещё может «глючить» |
|---|---|
| READ UNCOMMITTED | видны чужие незакоммиченные данные (грязное чтение) |
| READ COMMITTED *(по умолчанию в PG)* | перечитал строку — а она изменилась |
| REPEATABLE READ | при повторном запросе появились новые строки (фантомы) |
| SERIALIZABLE | ничего, как будто транзакции шли по очереди |

**Три аномалии простыми словами:**
- **грязное чтение** — прочитал то, что другой ещё не сохранил (и может отменить);
- **неповторяемое чтение** — та же строка при перечитывании изменилась;
- **фантомы** — повторный запрос вернул новые строки.

**Зачем.** Спросят уровень по умолчанию (READ COMMITTED в PostgreSQL) и какие аномалии бывают.

### 12. MVCC в PostgreSQL

**Простыми словами.** MVCC (многоверсионность) — хитрость, благодаря которой **читатели не блокируют писателей**, а писатели — читателей. Вместо блокировки PostgreSQL хранит **несколько версий строки**: каждая транзакция видит «снимок» данных на момент своего старта.

**Аналогия.** Как история версий документа: пока один редактирует новую версию, другой спокойно читает старую.

**Минус:** старые версии строк накапливаются («мёртвые» строки) — их убирает фоновый процесс `VACUUM` (autovacuum).

**🔍 Если копнут глубже:**
- У каждой версии строки есть служебные поля **xmin** (id транзакции, создавшей версию) и **xmax** (id удалившей). Транзакция видит версию, если она создана «видимой» транзакцией и ещё не удалена — это и есть проверка видимости по снимку.
- Из-за MVCC `READ UNCOMMITTED` в PostgreSQL ведёт себя как `READ COMMITTED` (грязного чтения просто нет), а `REPEATABLE READ` реально снапшотный — фантомов нет, но возможна `serialization failure` (нужно повторить транзакцию).
- **VACUUM** не только чистит мёртвые версии, но и обновляет статистику (для планировщика) и защищает от **transaction id wraparound** — переполнения счётчика транзакций (грозит остановкой БД, если autovacuum не справляется).
- **HOT-update** — оптимизация: если изменённые колонки не входят в индексы, новая версия строки кладётся на ту же страницу без обновления индексов (дешевле).

**Зачем.** Спросят «почему в PG чтение не ждёт запись» → MVCC. Плюс знать про VACUUM.

### 13. Lost update (потерянное обновление) и решения

**Простыми словами.** Два процесса прочитали баланс (1000), оба что-то прибавили/списали и оба записали свой результат — одно изменение **затёрлось**. Это та же гонка, что и `i++` в многопоточке, только в БД.

**Решения:**
```sql
-- ✅ 1) атомарный UPDATE (БД сама посчитает, без чтения в приложение):
UPDATE accounts SET balance = balance - 100 WHERE id = 1 AND balance >= 100;

-- ✅ 2) пессимистичная блокировка — конкурент ждёт:
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;  -- запер строку
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;

-- ✅ 3) оптимистичная блокировка — колонка version:
UPDATE accounts SET balance = 900, version = version + 1
WHERE id = 1 AND version = 7;  -- обновлено 0 строк → кто-то опередил → перечитать и повторить
```

**Зачем.** Главный банковский кейс (одновременное изменение баланса). Знай все три способа.

### 14. Deadlock в БД

**Простыми словами.** То же, что и в многопоточке: транзакция A заперла строку 1 и ждёт строку 2, а B заперла строку 2 и ждёт строку 1 — обе застряли. PostgreSQL это обнаруживает и **убивает одну** транзакцию с ошибкой `deadlock detected`.

**Профилактика:** обновляй строки **в одном порядке** (например, `ORDER BY id`), держи транзакции короткими, и на стороне приложения умей **повторить** убитую транзакцию.

**Зачем.** Связано с многопоточным deadlock (там вопрос 8). Главный приём тот же — единый порядок захвата.

## Проектирование

### 15. Нормальные формы и когда денормализовать

**Простыми словами.** Нормализация — раскладываем данные по таблицам без дублирования:
- **1НФ** — в ячейке одно значение (не список «телефон1, телефон2»);
- **2НФ** — нет зависимости от части составного ключа;
- **3НФ** — неключевые поля не зависят друг от друга (город хранится отдельно от региона).

**Денормализация** — намеренно продублировать данные ради **скорости чтения** (меньше JOIN). Цена — усложнение записи и риск рассинхрона. Применяют в отчётах, витринах, горячих путях чтения.

**Зачем.** Спросят «что такое 3НФ» и «зачем денормализация». Доводят обычно до 3НФ, денормализуют осознанно ради чтения.

### 16. UUID vs sequence для первичного ключа

**Простыми словами.**
- **Sequence (автоинкремент, bigint)** — числа по порядку 1,2,3… Компактно, вставки быстрые (новые строки идут «в конец» индекса). Но id предсказуем и неудобен при объединении данных из разных баз.
- **UUID** — длинный случайный идентификатор, можно сгенерить где угодно без БД. Минус: случайный UUID «рвёт» порядок индекса и замедляет вставку. Решение — **UUIDv7** (упорядочен по времени).

**Зачем.** Спросят выбор ключа. Ответ: bigint — по умолчанию; UUID — когда нужно генерить вне БД / в распределённой системе (лучше v7).

---

### 17. Партиционирование vs шардирование

**Простыми словами.**
- **Партиционирование** — разбиение одной большой таблицы на части **внутри одной БД** (например, по месяцам). Запросы за свежий месяц читают только нужную часть; старые данные легко удалить (`DROP PARTITION`).
- **Шардирование** — разнесение данных по **разным серверам** по ключу. Так масштабируют запись и объём, но запросы и транзакции «через шарды» становятся болью.

**Аналогия.** Партиционирование — один архив, разложенный по папкам-годам. Шардирование — архив, раскиданный по разным зданиям.

**Зачем.** Спросят разницу. Главное: партиции — в одной БД, шарды — на разных серверах.

---

### 18. Безопасные миграции при rolling-деплое (expand-contract)

**Простыми словами.** При выкатке без простоя какое-то время **работают одновременно старая и новая версии** кода. Значит, схема БД должна подходить обеим. Меняем в три шага:
1. **Expand** — добавили новое (nullable-колонку), пишем и в старое, и в новое;
2. **Migrate** — перелили данные, переключили чтение на новое;
3. **Contract** — когда старая версия везде ушла, удалили старое.

**Чего нельзя:** сразу делать `NOT NULL` без значения по умолчанию или `DROP/RENAME` колонки в одном релизе с кодом — старая версия сломается. Инструменты: Liquibase/Flyway.

**Зачем.** Senior-вопрос про эксплуатацию. Запомни схему expand → migrate → contract.

## NoSQL и распределённое

### 19. Стратегии кеширования и проблемы

**Простыми словами.** Кеш (Redis) хранит часто читаемое, чтобы не дёргать БД. Самый частый подход — **cache-aside**: читаем кеш → если там пусто (промах), идём в БД и кладём результат в кеш. При изменении данных кеш-ключ **удаляют** (а не обновляют — меньше гонок).

**Проблемы:**
- **устаревание** — в кеше старые данные (решает TTL — срок жизни);
- **cache stampede** — ключ протух, и толпа запросов разом ломится в БД (решают разбросом TTL и блокировкой на пересчёт);
- **согласованность** кеш↔БД — порядок: сначала пишем в БД, потом сбрасываем кеш.

**Зачем.** Спросят «как кешируешь» → cache-aside + TTL + инвалидация при записи.

---

### 20. CAP-теорема

**Простыми словами.** В распределённой системе из трёх свойств — **C**onsistency (все видят одни данные), **A**vailability (система всегда отвечает), **P**artition tolerance (работает при разрыве сети) — при разрыве сети (а он неизбежен) приходится выбирать между **C и A**:
- **CP** — лучше откажу в ответе, чем отдам устаревшее (ZooKeeper, банковские данные);
- **AP** — лучше отвечу, пусть и слегка устаревшим (Cassandra, DNS).

**Аналогия.** Связь между филиалами оборвалась. Банк скажет «операция недоступна» (CP — не рискнём отдать неверный баланс). Соцсеть покажет чуть устаревшую ленту (AP — лишь бы работало).

**Зачем.** Для денег обычно выбирают **C** (согласованность). Уточни на собесе: выбор актуален именно в момент разрыва сети.

## Как отвечать на собесе по БД

1. **SQL пиши вслух по порядку:** FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY.
2. **Знай 3 ловушки:** LEFT+WHERE превращается в INNER; NOT IN с NULL; функция над колонкой убивает индекс.
3. **Производительность:** «медленный запрос» → EXPLAIN ANALYZE → нет индекса / функция над колонкой / устаревшая статистика.
4. **Банковский кейс:** одновременное изменение баланса → атомарный UPDATE или блокировка (lost update).
