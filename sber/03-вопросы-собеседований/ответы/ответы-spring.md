# Spring — подробный разбор (для первого изучения)

Каждый вопрос: **простыми словами → подробнее → пример → зачем**. Список вопросов — в [spring.md](../spring.md).

> **Главная идея Spring.** Ты не создаёшь объекты сам через `new` — это делает «контейнер» Spring. Он создаёт объекты (бины), связывает их между собой и оборачивает в «обёртки» (прокси), которые добавляют магию: транзакции, кеширование, безопасность. Понимание прокси — ключ ко всему Spring.

---

## ⚠️ Вопрос-убийца: self-invocation в @Transactional

### 1. Self-invocation — почему транзакция «не сработала»

**Простыми словами.** Аннотации `@Transactional`, `@Cacheable`, `@Async` работают через **прокси** — обёртку вокруг твоего объекта. Магия срабатывает, только когда вызов приходит **снаружи** (через обёртку). Если метод вызывает другой метод **того же класса через `this`**, вызов идёт напрямую, мимо обёртки — и аннотация **молча не работает**.

**Аналогия.** Прокси — это секретарь у двери кабинета. Если посетитель заходит через секретаря — тот оформляет документы. Но если ты уже внутри кабинета и ходишь из комнаты в комнату (`this`), секретарь об этом не знает и ничего не оформляет.

**Пример проблемы:**
```java
@Service
public class PaymentService {
    public void process(Payment p) {
        validate(p);
        this.save(p);     // ❌ вызов через this мимо прокси — транзакции НЕ будет!
    }
    @Transactional
    public void save(Payment p) {...}
}
```

**Решение (лучшее) — вынести метод в отдельный бин:**
```java
@Service
public class PaymentService {
    private final PaymentSaver saver;          // отдельный бин = отдельный прокси
    public void process(Payment p) { saver.save(p); } // вызов снаружи — работает
}
```

**Схема:**
```
Внешний вызов (РАБОТАЕТ):
  клиент ──> [ Proxy ] ──открыть транзакцию──> PaymentService.save()   ✅

Self-invocation (НЕ работает):
  PaymentService.process()
        │  this.save()   (мы уже ВНУТРИ объекта)
        ▼
     save()                                                            ❌ мимо прокси → tx нет
```

**🔍 Если копнут глубже:**
- По умолчанию прокси работает в режиме **proxy-based AOP** (Spring AOP). Полностью обойти ограничение self-invocation можно через **AspectJ load/compile-time weaving** — там аннотации вшиваются прямо в байткод, и работает даже `this.method()`. Но это редкость, обычно проще вынести бин.
- Та же ловушка у `@Cacheable`, `@Async`, `@Retryable`, `@PreAuthorize` — у всего, что построено на прокси.
- `private`-методы и `final`-методы/классы не проксируются (CGLIB не может их переопределить) — аннотации на них молча не сработают.

**Зачем.** Это вопрос-«отсеиватель». Если поймёшь его — поймёшь, как вообще работает Spring. Запомни: **аннотации работают только при внешнем вызове через прокси**.

## IoC и бины

### 2. Что такое IoC и DI

**Простыми словами.**
- **IoC (Inversion of Control, инверсия управления)** — «не ты создаёшь объекты, а контейнер за тебя». Управление перевёрнуто: раньше класс сам делал `new`, теперь это делает Spring.
- **DI (Dependency Injection, внедрение зависимостей)** — конкретный способ IoC: нужные объекты тебе **дают извне**, а не создаёшь внутри.

**Аналогия.** Вместо того чтобы самому идти и собирать двигатель для машины (`new Engine()`), тебе его **привозят и вставляют** на заводе. Ты просто говоришь «мне нужен двигатель».

```java
// ❌ без DI: класс сам создаёт зависимость, жёстко связан
class OrderService {
    private final SmsClient sms = new SmsClient();
}
// ✅ с DI: зависимость внедряется, можно подменить (например, в тесте)
class OrderService {
    private final Notifier notifier;
    OrderService(Notifier notifier) { this.notifier = notifier; }
}
```

**Зачем.** Это суть Spring. Даёт слабую связанность и лёгкое тестирование (можно подсунуть заглушку).

### 3. Почему конструкторное внедрение лучше

**Простыми словами.** Зависимости можно внедрять тремя способами: через конструктор, сеттер или прямо в поле. **Конструктор — лучший**, потому что:
- поля можно сделать `final` (никто не подменит после создания);
- зависимость **обязательна** — объект нельзя создать без неё в «сломанном» виде;
- легко тестировать — просто `new OrderService(mockNotifier)` без Spring;
- циклические зависимости сразу видны как ошибка (а это сигнал плохого дизайна).

```java
@Service
class OrderService {
    private final Notifier notifier;            // final — гарантированно задан
    OrderService(Notifier notifier) { this.notifier = notifier; }
}
```

**Зачем.** Спросят «как внедряешь зависимости и почему». Правильный ответ — через конструктор.

### 4. Жизненный цикл бина

**Простыми словами.** Бин (объект под управлением Spring) проходит этапы «рождения»:
1. **создание** объекта;
2. **внедрение зависимостей**;
3. **`@PostConstruct`** — твой метод «настройся после создания»;
4. оборачивание в **прокси** (вот тут добавляется транзакционность и т.п.);
5. **использование**;
6. **`@PreDestroy`** — «приберись перед удалением».

**Схема:**
```
new → внедрение зависимостей → @PostConstruct → [ ОБЁРТКА В PROXY ] → готов → @PreDestroy
                                                  ▲
                          здесь добавляются @Transactional / @Cacheable / @Async
```

**Зачем.** Объясняет, на каком этапе появляется прокси (а значит — почему работают аннотации). Спросят «где можно сделать инициализацию» → `@PostConstruct`.

### 5. Scope бинов и ловушка prototype в singleton

**Простыми словами.** Scope — «сколько экземпляров бина создаётся»:
- **singleton** (по умолчанию) — **один на всё приложение**;
- **prototype** — **новый при каждом запросе** бина;
- **request/session** — для веба (на запрос/сессию).

**Ловушка.** Если prototype-бин внедрить в singleton **обычным способом**, он создастся **один раз** (когда создавался singleton) и больше не обновится. Чтобы получать новый каждый раз — нужен `ObjectProvider`.

```java
@Service
class ReportService {
    private final ObjectProvider<ReportGenerator> generators;
    void build() {
        ReportGenerator g = generators.getObject(); // ✅ новый экземпляр на каждый вызов
    }
}
```

**Зачем.** Тонкое место. Главное запомни: singleton живёт один на всех, и внутри него prototype «застывает».

### 6. Как Spring разрешает циклические зависимости

**Простыми словами.** Циклическая зависимость — A нужен B, а B нужен A. Spring умеет это «распутать» при внедрении через сеттер/поле (выдаёт временную недостроенную ссылку), но **не может** при конструкторном внедрении — там сразу ошибка.

**Это хорошо:** ошибка заставляет пересмотреть дизайн (цикл — обычно признак, что классы стоит разделить).

**Зачем.** Покажет понимание. Лучший ответ: «цикл лучше убрать рефакторингом, а не лечить костылями».

### 7. @Component vs @Bean

**Простыми словами.** Оба создают бин, но:
- **@Component** — вешаешь **на свой класс**, Spring находит его сканированием.
- **@Bean** — метод в конфиге, которым ты **вручную создаёшь** бин. Нужен для **чужих классов** (из библиотек), на которые нельзя повесить аннотацию, и для сложной настройки.

```java
@Component                       // мой класс — Spring найдёт сам
class MyService {}

@Configuration
class Config {
    @Bean                        // чужой класс из библиотеки — создаю руками
    ObjectMapper objectMapper() { return new ObjectMapper(); }
}
```

**Зачем.** Запомни: свой код → @Component, чужой/сложная настройка → @Bean.

## Прокси и AOP

### 8. JDK proxy vs CGLIB

**Простыми словами.** Spring делает обёртки (прокси) двумя способами:
- **JDK dynamic proxy** — работает, если у бина есть **интерфейс** (обёртка реализует тот же интерфейс).
- **CGLIB** — **наследует класс** бина (по умолчанию в Spring Boot).

**Следствия CGLIB:** нельзя проксировать `final`-класс или `final`-метод (наследоваться нельзя), `private`-методы не перехватываются.

**Зачем.** Объясняет ограничения: почему `final`/`private` ломают аннотации. Связано с self-invocation.

## Транзакции

### 9. Propagation (распространение транзакций) — 7 видов

**Простыми словами.** Propagation отвечает на вопрос: «метод вызвали внутри уже идущей транзакции — что делать?». Главные:
- **REQUIRED** (по умолчанию) — «есть транзакция — присоединюсь, нет — создам новую»;
- **REQUIRES_NEW** — «всегда создаю **свою отдельную** транзакцию» (внешнюю приостанавливаю);
- **NESTED** — «вложенная с точкой сохранения (savepoint)»: её можно откатить, не откатывая внешнюю;
- остальные (SUPPORTS, NOT_SUPPORTED, MANDATORY, NEVER) — для особых случаев.

**Зачем.** Спросят минимум про REQUIRED и REQUIRES_NEW. Знай эти два уверенно.

---

### 10. NESTED vs REQUIRES_NEW

**Простыми словами.**
- **REQUIRES_NEW** — **полностью независимая** транзакция. Закоммитится сама, даже если внешняя потом откатится.
- **NESTED** — часть внешней, но с «точкой сохранения». Откат вложенной не валит внешнюю, но коммит — только вместе с внешней.

**Пример (зачем нужно REQUIRES_NEW):**
```java
@Transactional
public void processPayment(Payment p) {
    pay(p);
    audit.log(p);   // аудит должен сохраниться, ДАЖЕ если pay() потом откатится
}

@Service
class AuditService {
    @Transactional(propagation = Propagation.REQUIRES_NEW) // независимый коммит
    public void log(Payment p) { auditRepo.save(...); }
}
```

**Зачем.** Классический кейс: «лог/аудит должен сохраниться независимо от основной операции» → REQUIRES_NEW.

### 11. Когда @Transactional НЕ откатывает (важно!)

**Простыми словами.** По умолчанию Spring откатывает транзакцию **только на unchecked-исключениях** (`RuntimeException`). На **checked-исключениях** (например, `IOException`) — **НЕ откатывает**, а коммитит. Это сюрприз для многих.

**Пример:**
```java
@Transactional                  // ❌ на IOException будет КОММИТ, а не откат
public void transfer() throws IOException { ... }

@Transactional(rollbackFor = Exception.class)  // ✅ теперь откатит и на checked
public void transfer() throws IOException { ... }
```

**Другие причины «не откатилось»:** self-invocation (вопрос 1), не-public метод, исключение проглотили в `try/catch`.

**🔍 Если копнут глубже:**
- **Физическая vs логическая транзакция:** при `REQUIRED` вложенный метод присоединяется к той же *физической* транзакции. Если вложенный бросит исключение и его поймать снаружи — транзакция всё равно помечена `rollback-only`, и на коммите вылетит `UnexpectedRollbackException` («хотел закоммитить, а транзакция уже обречена»).
- **Где хранится транзакция:** Spring кладёт соединение/ресурсы в `ThreadLocal` (`TransactionSynchronizationManager`) — поэтому транзакция «живёт» в рамках потока. При уходе работы в другой поток (новый thread, `@Async`) транзакция **не передаётся**.
- `@TransactionalEventListener(phase = AFTER_COMMIT)` — выполнить логику только после успешного коммита (например, отправить событие, когда данные точно сохранены).
- Транзакция стартует на **первом** вызове через прокси с `@Transactional`; вложенные `REQUIRED` её переиспользуют — вот почему важен propagation.

**Зачем.** Топ-вопрос. Запомни: **по умолчанию откат только на RuntimeException**; для checked нужен `rollbackFor`.

### 12. Что делает readOnly=true

**Простыми словами.** `@Transactional(readOnly = true)` — подсказка «эта транзакция только читает». Hibernate отключает отслеживание изменений (не тратит ресурсы), БД может оптимизировать, в кластере запрос можно отправить на реплику.

**Важно:** это **оптимизация, а не защита** — запись в некоторых конфигурациях физически возможна.

**Зачем.** Спросят «зачем readOnly» → ответ: оптимизация запросов на чтение.

## Spring Boot

### 13. Как работает автоконфигурация

**Простыми словами.** Spring Boot сам настраивает кучу вещей «из коробки»: увидел в зависимостях драйвер БД — настроил подключение; увидел веб — поднял сервер. Это и есть **автоконфигурация**: набор готовых конфигов, каждый включается **по условию** (`@ConditionalOnClass`, `@ConditionalOnMissingBean`).

**Важно:** твой бин «побеждает» автоконфигурационный — если ты определил свой, Spring не создаёт дефолтный (`@ConditionalOnMissingBean`).

**Отладка:** запусти с `--debug` → увидишь отчёт, что и почему включилось.

**Зачем.** Спросят «как Boot всё настраивает сам» → условные конфигурации по наличию классов/бинов.

---

### 14. @ConfigurationProperties vs @Value

**Простыми словами.**
- **@Value** — вытащить **одно** свойство: `@Value("${app.timeout}")`.
- **@ConfigurationProperties** — связать **целую группу** свойств с объектом (типизированно, с валидацией).

```java
@ConfigurationProperties(prefix = "app.payment")
class PaymentProps {
    private Duration timeout;        // app.payment.timeout
    private int retries;             // app.payment.retries
}
```

**Зачем.** Для группы связанных настроек — всегда `@ConfigurationProperties` (типобезопасно, удобно).

## Spring MVC / REST

### 15. Путь HTTP-запроса в Spring MVC

**Простыми словами.** Запрос проходит конвейер:
1. **фильтры** (до Spring) — аутентификация, логирование, CORS;
2. **DispatcherServlet** — главный диспетчер, принимает все запросы;
3. **HandlerMapping** — находит нужный контроллер по URL;
4. **преобразование тела** (`@RequestBody` → объект через JSON);
5. **метод контроллера** — твоя логика;
6. **сериализация ответа** (объект → JSON).

**Схема:**
```
HTTP-запрос
   ▼
[Фильтры сервлета]  (auth, CORS, логирование — до Spring)
   ▼
[DispatcherServlet]  ← центральный диспетчер
   ▼
[HandlerMapping]  найти контроллер по URL
   ▼
[@RequestBody: JSON → объект]  через HttpMessageConverter
   ▼
[метод контроллера]  ← твоя логика
   ▼
[объект → JSON]  сериализация ответа
   ▼
HTTP-ответ
```

**Зачем.** Понимание «как запрос доходит до контроллера». Спросят про роль DispatcherServlet — это центральный диспетчер.

---

### 16. Централизованная обработка ошибок REST

**Простыми словами.** Чтобы не писать `try/catch` в каждом контроллере, есть **`@RestControllerAdvice`** — одно место, где ловятся исключения со всего приложения и превращаются в аккуратные HTTP-ответы.

```java
@RestControllerAdvice
class ErrorHandler {
    @ExceptionHandler(NotFoundException.class)
    ResponseEntity<?> handle(NotFoundException e) {
        return ResponseEntity.status(404).body(...);
    }
}
```
Маппинг: валидация → 400, не найдено → 404, конфликт → 409, бизнес-ошибка → 422.

**Зачем.** Хороший тон. Спросят «как обрабатываешь ошибки в REST» → централизованно через `@RestControllerAdvice`.

### 17. Фильтр vs интерцептор vs AOP

**Простыми словами.** Три уровня, где можно «вклиниться» в обработку:
- **Фильтр** — самый ранний, на уровне сервлета, ещё до Spring (auth, CORS, логирование).
- **Интерцептор** — вокруг контроллера, знает, какой контроллер вызывается.
- **AOP (аспект)** — вокруг **любых** бинов (не только веб), по правилу (pointcut).

Порядок: фильтр → интерцептор → аспект → метод.

**Зачем.** Спросят «чем фильтр отличается от интерцептора» → фильтр раньше и не знает о Spring MVC, интерцептор знает о контроллере.

## Spring Data JPA

### 18. Жизненный цикл JPA-сущности

**Простыми словами.** Объект-сущность бывает в состояниях:
- **transient** — только что создан через `new`, Spring о нём не знает;
- **managed** — под управлением (после `save`/`find`): изменения **автоматически** сохраняются в БД (dirty checking);
- **detached** — управление закончилось (транзакция закрыта): изменения уже не сохраняются;
- **removed** — помечен на удаление.

**Ключевое:** у managed-объекта достаточно изменить поле — Spring сам сделает UPDATE.

**Зачем.** Объясняет «почему изменения то сохраняются, то нет» — зависит от состояния.

### 19. LazyInitializationException

**Простыми словами.** Связанные данные (например, позиции заказа) часто грузятся **лениво** — только при обращении. Если обратиться к ним **после закрытия транзакции** — будет `LazyInitializationException` («сессия уже закрыта, не могу догрузить»).

**Решения:** загрузить сразу через `JOIN FETCH` или `@EntityGraph`, либо отдавать DTO.

```java
@EntityGraph(attributePaths = "items")   // загрузит items сразу, одним запросом
List<Order> findByStatus(OrderStatus s);
```

**Зачем.** Очень частая ошибка новичков с JPA. Запомни причину: обращение к lazy-связи вне транзакции.

### 20. Проблема N+1

**Простыми словами.** Берёшь список из 100 заказов (1 запрос), потом для каждого обращаешься к его позициям — и получаешь **ещё 100 запросов**. Итого 1+100 = 101 запрос вместо одного-двух. Это бьёт по производительности.

**Симптом:** в логах SQL куча одинаковых запросов.

```java
List<Order> orders = orderRepo.findAll();   // 1 запрос
orders.forEach(o -> o.getItems().size());   // ❌ +N запросов

// ✅ один запрос через JOIN FETCH
@Query("select distinct o from Order o join fetch o.items")
List<Order> findWithItems();
```

**Зачем.** Топ-вопрос по JPA. Умей объяснить симптом и решение (JOIN FETCH / @EntityGraph).

### 21. Оптимистичная vs пессимистичная блокировка

**Простыми словами.** Что делать, если два пользователя одновременно меняют одну запись?
- **Оптимистичная** (`@Version`) — «надеемся, что конфликтов мало». При сохранении проверяется версия; если кто-то успел изменить — ошибка, и ты повторяешь. Дёшево, для редких конфликтов.
- **Пессимистичная** (`SELECT FOR UPDATE`) — «сразу запираем строку», остальные ждут. Для «горячих» строк (остаток на счёте).

**Аналогия.** Оптимистичная — редактируешь вики и при сохранении узнаёшь «кто-то уже поменял, обнови». Пессимистичная — «занял документ, остальные ждут».

**Зачем.** Банковский кейс (остатки на счетах) → часто пессимистичная. Знай оба подхода.

### 22. save vs saveAndFlush, findById vs getReferenceById

**Простыми словами.**
- **save** — кладёт в контекст, SQL уйдёт позже (при flush/commit). **saveAndFlush** — отправляет SQL немедленно (если нужно сразу поймать ошибку БД).
- **findById** — реально идёт в БД и достаёт объект. **getReferenceById** — возвращает «ленивую заглушку» без запроса (полезно, чтобы проставить внешний ключ, не читая всю запись).

**Зачем.** Тонкости для middle. Запомни: getReferenceById не делает запрос сразу.

### 23. Кеши Hibernate (1-го и 2-го уровня)

**Простыми словами.**
- **Кеш 1-го уровня** — в рамках одной транзакции/сессии, **всегда включён**. Повторный `findById` того же объекта не пойдёт в БД.
- **Кеш 2-го уровня** — **между** сессиями (общий), включается явно (Caffeine/Redis). Ускоряет, но требует осторожности с инвалидацией в кластере.

**Зачем.** Спросят «почему второй find не сделал SQL» → кеш 1-го уровня.

## Spring Security

### 24. Как устроена Spring Security

**Простыми словами.** Spring Security — это **цепочка фильтров** перед твоими контроллерами. Она сначала выясняет «кто ты» (аутентификация), кладёт это в `SecurityContext`, потом проверяет «что тебе можно» (авторизация).

Метод-уровневая защита: `@PreAuthorize("hasRole('ADMIN')")` — но она работает через **прокси**, то есть подвержена той же ловушке self-invocation (вопрос 1).

**Зачем.** Спросят про разделение аутентификация/авторизация и что это цепочка фильтров.

---

### 25. JWT vs сессии

**Простыми словами.**
- **Сессия** — сервер хранит состояние пользователя, выдаёт ему id сессии в куке. Легко «выкинуть» пользователя, но в кластере нужно общее хранилище сессий.
- **JWT** — самодостаточный подписанный токен, сервер **ничего не хранит** (stateless). Хорошо масштабируется, но «отозвать» токен сложно (решают коротким сроком жизни + refresh-токеном).

**Аналогия.** Сессия — «список гостей у охранника» (можно вычеркнуть). JWT — «браслет с печатью на входе» (охранник не помнит тебя, просто проверяет печать).

**Зачем.** В микросервисах обычно JWT/OAuth2. Знай плюс stateless и минус «сложно отозвать».

## Как отвечать на собесе по Spring

1. **Всё крутится вокруг прокси.** Транзакции, кеш, security, @Async — через обёртки. Поймёшь прокси — поймёшь self-invocation, JDK/CGLIB, @Transactional.
2. **Знай 3 «вопроса-убийцы»:** self-invocation, откат только на RuntimeException, N+1.
3. **Внедрение зависимостей** — через конструктор, всегда.
4. **Давай примеры из своего проекта** — где использовал @Transactional, как ловил ошибки.
