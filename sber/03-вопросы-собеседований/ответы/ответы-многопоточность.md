# Многопоточность — подробный разбор (для первого изучения)

Самая «страшная» тема для новичков. Здесь много аналогий, чтобы стало понятно. Список вопросов — в [многопоточность.md](../многопоточность.md).

> **Главная идея темы.** Поток (thread) — это «отдельный работник», выполняющий код. Если работников несколько и они трогают одни и те же данные — начинаются проблемы (как два повара тянутся к одной кастрюле). Вся многопоточность — про то, как их «помирить».

---

## База

### 1. Thread, Runnable, Callable

**Простыми словами.**
- **Runnable** — «задача, которую надо сделать» (без результата). Просто «сделай и всё».
- **Callable<V>** — задача, которая **возвращает результат** и может бросить исключение. Результат забираешь потом через `Future`.
- **Thread** — сам «работник» (поток). Наследоваться от него не нужно — задачу отдают пулу потоков.

**Пример:**
```java
Runnable task = () -> System.out.println("работаю");      // ничего не возвращает
Callable<Integer> calc = () -> 2 + 2;                      // вернёт 4
Future<Integer> future = executor.submit(calc);
int result = future.get();                                // заберём результат (4)
```

**Зачем.** Базовый вопрос. Запомни: нужен результат → Callable, не нужен → Runnable.

---

### 2. start() vs run()

**Простыми словами.** `start()` — запускает **новый поток** и выполняет код в нём (параллельно). `run()` — это просто **обычный вызов метода** в текущем потоке, никакой параллельности.

**Аналогия.** `start()` — нанять второго работника. `run()` — сделать работу самому.

```java
new Thread(task).start();  // ✅ задача побежит в отдельном потоке
new Thread(task).run();    // ❌ ошибка новичка: выполнится здесь же, последовательно
```
Повторно вызвать `start()` нельзя — будет `IllegalThreadStateException`.

**Зачем.** Очень частая ловушка. Запомни: параллельность даёт только `start()`.

---

### 3. Состояния потока

**Простыми словами.** Поток за свою жизнь проходит через состояния:
- **NEW** — создан, но не запущен;
- **RUNNABLE** — работает или готов работать;
- **BLOCKED** — ждёт, пока освободится замок (монитор);
- **WAITING / TIMED_WAITING** — ждёт сигнала (бессрочно или с таймаутом, например `sleep`);
- **TERMINATED** — завершился.

**Схема:**
```
         start()                       монитор освободился
  NEW ───────────> RUNNABLE <──────────────────────────── BLOCKED
                    │   ▲                                    ▲
   wait()/join()/   │   │ notify()/                          │ ждёт замок
   sleep()          ▼   │ время вышло                        │ (synchronized занят)
            WAITING / TIMED_WAITING ─────────────────────────┘
                    │
          код метода завершился
                    ▼
               TERMINATED
```

**Зачем.** Помогает читать thread dump (снимок потоков) при разборе зависаний. Если много потоков в `BLOCKED` — конкуренция за один замок; в `WAITING` — ждут условие/ответ.

### 4. happens-before — «что гарантированно видно»

**Простыми словами.** Это правило модели памяти Java (JMM): оно говорит, **когда изменения, сделанные одним потоком, гарантированно увидит другой**. Без таких правил один поток может не увидеть, что другой что-то поменял (из-за кешей процессора).

**Аналогия.** Ты записал заметку, но коллега видит её, только если ты «официально передал» её через определённый канал. happens-before — список таких «официальных каналов»:
- запись в `volatile` → последующее чтение этой переменной;
- выход из `synchronized` → следующий вход в тот же замок;
- `start()` потока → код внутри потока;
- код потока → `join()` после него.

**🔍 Если копнут глубже:**
- Без happens-before компилятор и процессор могут **переупорядочивать** инструкции и кешировать значения в регистрах — поэтому поток B может «не увидеть» запись потока A, хотя по коду она была раньше.
- **Семантика volatile:** запись volatile-переменной = «барьер записи» (всё, что было до, становится видимым), чтение = «барьер чтения». Поэтому флаг через volatile работает, а просто поле — нет.
- **Гарантия final-полей:** если объект корректно опубликован, другие потоки **гарантированно** видят инициализированные `final`-поля — основа потокобезопасности иммутабельных объектов (вопрос 10).
- happens-before **транзитивно:** A→B и B→C ⇒ A→C. На этом строятся все безопасные «передачи» данных между потоками через volatile/локи/очереди.

**Зачем.** Это теоретическое ядро темы. Достаточно объяснить смысл: «гарантия видимости изменений между потоками».

### 5. Что гарантирует volatile (и чего НЕ гарантирует)

**Простыми словами.** `volatile` у переменной означает «всегда читай свежее значение из общей памяти, не из локального кеша потока». Это решает проблему **видимости**.

**Но!** `volatile` **не делает операцию атомарной**. `counter++` — это на самом деле три действия (прочитать → прибавить → записать), и два потока всё равно могут «затереть» друг друга.

**Пример:**
```java
private volatile boolean running = true;  // ✅ идеально для флага-выключателя
public void stop() { running = false; }   // другой поток точно увидит изменение

private volatile int counter = 0;
counter++;                                // ❌ гонка осталась! это read-modify-write

private final AtomicInteger c = new AtomicInteger();
c.incrementAndGet();                      // ✅ вот это атомарно
```

**Зачем.** Топ-вопрос. Запомни формулу: **volatile = видимость, но НЕ атомарность**.

### 6. Как работает synchronized

**Простыми словами.** `synchronized` — это «замок»: только один поток за раз может войти в защищённый блок. Остальные ждут снаружи. Даёт сразу две вещи: **взаимное исключение** (никто не лезет одновременно) и **видимость** (изменения видны следующему вошедшему).

**Аналогия.** Туалет с замком: внутри один человек, остальные ждут в очереди.

**Детали:**
- замок берётся на объекте: метод — на `this`, статический метод — на классе, блок — на указанном объекте;
- **реентерабельность** — поток, уже держащий замок, может войти в другой synchronized на том же объекте (не заблокирует сам себя).

```java
synchronized (account) {  // только один поток одновременно меняет счёт
    account.balance += amount;
}
```

**Зачем.** Базовый инструмент синхронизации. Спросят «что даёт synchronized» — отвечай: взаимное исключение + видимость.

### 7. Почему wait() только внутри synchronized и в цикле

**Простыми словами.** `wait()` усыпляет поток до сигнала `notify()`. Чтобы их использовать, поток **обязан владеть замком** объекта — иначе `IllegalMonitorStateException`.

И проверять условие надо **в цикле `while`**, а не `if`, по двум причинам:
1. бывают «ложные пробуждения» (поток проснулся без сигнала);
2. пока поток просыпался, другой мог снова изменить условие.

```java
synchronized (queue) {
    while (queue.isEmpty()) {   // именно while, не if!
        queue.wait();
    }
    var item = queue.poll();
}
```

**Зачем.** Каверзный вопрос «почему while, а не if». Запомни про ложные пробуждения.

### 8. Deadlock (взаимная блокировка) и как избежать

**Простыми словами.** Deadlock — когда два потока намертво ждут друг друга и никто не двигается. Поток A держит замок 1 и ждёт замок 2, а поток B держит замок 2 и ждёт замок 1.

**Аналогия.** Два человека в узком коридоре уступают друг другу и оба стоят. Или: ты держишь вилку и ждёшь нож, сосед держит нож и ждёт вилку.

**Как избежать (главный приём):** всегда захватывать замки **в одном и том же порядке**. Например, для счетов — по возрастанию id.

```java
// ❌ перевод A→B и B→A одновременно = deadlock
synchronized (from) { synchronized (to) { ... } }

// ✅ всегда сначала меньший id, потом больший — цикла ожидания не возникнет
Account first  = from.id() < to.id() ? from : to;
Account second = from.id() < to.id() ? to : from;
synchronized (first) { synchronized (second) { ... } }
```
Другие приёмы: `tryLock` с таймаутом, один общий замок. Диагностика: thread dump — JVM сама пишет «Found one Java-level deadlock».

**Зачем.** Любимый банковский кейс (перевод между счетами). Запомни «единый порядок захвата».

### 9. Race condition: check-then-act

**Простыми словами.** Гонка (race condition) — когда результат зависит от того, кто из потоков успел первым. Частый случай — «проверил, потом сделал»: между проверкой и действием встревает другой поток.

**Пример:**
```java
// ❌ между if и put другой поток уже мог положить значение
if (!cache.containsKey(key)) cache.put(key, loadExpensive(key));

// ✅ атомарная операция: проверка и вставка как одно целое
cache.computeIfAbsent(key, k -> loadExpensive(k));
```

**Аналогия.** Двое одновременно видят «последнее место свободно» и оба садятся.

**Зачем.** Очень частая реальная ошибка. Решение — атомарные методы (`putIfAbsent`, `computeIfAbsent`) или synchronized.

---

### 10. Безопасная публикация объекта

**Простыми словами.** «Опубликовать» объект — сделать ссылку на него видимой другим потокам. Опасность: другой поток может увидеть объект **недостроенным** (конструктор ещё не закончился).

**Как безопасно:** `final`-поля, `volatile`-ссылка, статический инициализатор, передача через потокобезопасные коллекции. **Самый надёжный способ — делать объекты иммутабельными** (см. Java Core, вопрос 6): их в принципе нельзя испортить.

**Зачем.** Связывает иммутабельность и многопоточность — сильный ответ.

## java.util.concurrent (готовые инструменты)

### 11. ThreadPoolExecutor — пул потоков и судьба задачи

**Простыми словами.** Создавать поток на каждую задачу дорого. Пул — это «бригада работников», которые переиспользуются. Главные настройки: `corePoolSize` (постоянные работники), `maximumPoolSize` (максимум), очередь задач.

**Куда попадает новая задача (важная логика):**
1. работников меньше core → создаётся новый;
2. иначе → задача встаёт в очередь;
3. очередь полна, а работников меньше max → создаётся новый;
4. всё забито → срабатывает политика отказа (бросить исключение / выполнить в вызывающем потоке).

```java
var pool = new ThreadPoolExecutor(
    4, 16, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000),               // ⚠️ очередь с лимитом — обязательно
    new ThreadPoolExecutor.CallerRunsPolicy());   // при перегрузке притормозить источник
```

**Схема (куда попадёт задача):**
```
новая задача
   │
   ▼
потоков < core? ──да──> создать поток и выполнить
   │ нет
   ▼
очередь не полна? ──да──> положить в очередь
   │ нет
   ▼
потоков < max? ──да──> создать поток
   │ нет
   ▼
политика отказа (Abort / CallerRuns / Discard / DiscardOldest)
```

**Ловушка.** С **безлимитной** очередью (`new LinkedBlockingQueue<>()`) maximumPoolSize **никогда не сработает** — очередь не переполнится, а память будет течь.

**🔍 Если копнут глубже:**
- Тип очереди меняет поведение: `SynchronousQueue` (очередь «без места») → каждая задача требует свободного потока → пул растёт до max (так работает `newCachedThreadPool`). `ArrayBlockingQueue` (ограниченная) → back-pressure. `LinkedBlockingQueue` без лимита → пул не растёт сверх core.
- `allowCoreThreadTimeOut(true)` — даёт «гаснуть» и core-потокам при простое; `prestartAllCoreThreads()` — наоборот, прогреть заранее.
- **Размер пула:** для CPU-bound ≈ числу ядер; для IO-bound — больше (потоки в основном ждут). Формула Литтла: потоки ≈ целевой RPS × среднее время ответа.
- `CallerRunsPolicy` — изящный back-pressure: при перегрузке задачу выполняет вызывающий поток, тем самым притормаживая приём новых.

**Зачем.** Сильный практический вопрос. Запомни про ограниченную очередь.

### 12. Готовые пулы из Executors

**Простыми словами.** Фабрика `Executors` даёт быстрые варианты пулов, но у каждого есть подвох:
- **newFixedThreadPool(N)** — N потоков, но **безлимитная очередь** → риск OutOfMemory;
- **newCachedThreadPool** — плодит потоки по требованию → риск «взрыва» потоков;
- **newScheduledThreadPool** — для задач по расписанию;
- **ForkJoinPool** — для дробления больших задач (work-stealing).

**Совет на собес:** в проде лучше явный `ThreadPoolExecutor` с **ограниченной очередью**.

**Зачем.** Покажет, что ты знаешь подводные камни «удобных» фабрик.

---

### 13. CompletableFuture: thenApply / thenCompose / thenCombine

**Простыми словами.** `CompletableFuture` — способ описать асинхронную цепочку «сделай это, потом то». Методы:
- **thenApply** — преобразовать результат (как `map`);
- **thenCompose** — запустить **следующий асинхронный шаг** (как `flatMap`, чтобы не получить «future внутри future»);
- **thenCombine** — объединить результаты **двух независимых** задач.

```java
CompletableFuture<Client> client = supplyAsync(() -> loadClient(id), pool);
CompletableFuture<List<Account>> accounts =
    client.thenCompose(c -> loadAccountsAsync(c));   // следующий async-шаг

CompletableFuture<BigDecimal> rate = supplyAsync(this::loadRate, pool);
accounts.thenCombine(rate, (acc, r) -> convert(acc, r)) // два независимых результата
        .exceptionally(ex -> fallback())               // запасной вариант при ошибке
        .join();
```

**Зачем.** Тема для middle+. Запомни аналогию с map/flatMap из Stream.

### 14. CAS, AtomicLong vs LongAdder

**Простыми словами.** **CAS (Compare-And-Swap)** — «атомарно: замени значение, только если оно всё ещё такое, как я ожидал; если кто-то успел поменять — попробуй снова». Это работа **без замков** (оптимистично).

**Аналогия.** Редактируешь общий документ: «сохранить, если с момента открытия никто не менял; иначе перечитай и попробуй снова».

- **AtomicLong** — один счётчик; при большой конкуренции потоки «толкаются» на CAS.
- **LongAdder** — разбивает счётчик на несколько ячеек (каждый поток в свою), складывает при чтении. Быстрее для частых инкрементов (метрики).

**🔍 Если копнут глубже:**
- **Проблема ABA:** значение было A, кто-то сменил его на B и обратно на A — CAS «не заметит» подмены и пройдёт, хотя состояние между делом менялось. Лечится версией/меткой: `AtomicStampedReference` (значение + «штамп»).
- CAS под **высокой конкуренцией** деградирует: много потоков крутятся в цикле повторов («busy spin»), жгут CPU. Именно поэтому `LongAdder` (раскладка по ячейкам) обгоняет `AtomicLong` на счётчиках с частой записью.
- На уровне процессора CAS — это инструкция вроде `CMPXCHG` (x86); она атомарна аппаратно, без блокировок ОС.
- Atomic-классы дают и **видимость** (как volatile), и **атомарность** — поэтому заменяют связку «volatile + synchronized» для простых счётчиков/флагов.

**Зачем.** CAS — основа всех Atomic-классов и lock-free алгоритмов.

### 15. ReentrantLock vs synchronized

**Простыми словами.** `ReentrantLock` — это «продвинутый замок» с дополнительными возможностями, которых нет у `synchronized`:
- **tryLock** — попробовать взять замок с таймаутом (не зависать вечно);
- прерываемость, честная очередь (fair), несколько условий на один замок.

**Минус:** надо вручную освобождать в `finally`:
```java
lock.lock();
try { /* работа */ } finally { lock.unlock(); } // забудешь — навечно заблокируешь
```

**Правило.** Используй `synchronized` (проще, не «утечёт»), а `ReentrantLock` — когда нужны его особые фичи (таймаут и т.п.).

**Зачем.** Частое сравнение. Главное: synchronized по умолчанию, ReentrantLock когда нужен tryLock.

### 16. CountDownLatch vs CyclicBarrier vs Semaphore

**Простыми словами.** Три «координатора» потоков:
- **CountDownLatch** — «ждём, пока произойдёт N событий» (одноразовый). Пример: старт обработки после загрузки 3 конфигов.
- **CyclicBarrier** — «ждём, пока соберётся N потоков, потом все идут дальше» (переиспользуемый). Пример: фазы расчёта.
- **Semaphore** — «выдаём N пропусков», ограничивает число одновременных. Пример: не больше 10 запросов к внешнему сервису сразу.

**Аналогия.** Latch — «ждём, пока соберутся все гости, потом начинаем». Semaphore — «в зал пускаем только по 10 пропускам».

**Зачем.** Спросят «как ограничить число параллельных вызовов» → Semaphore.

### 17. Как устроен ConcurrentHashMap

**Простыми словами.** Это потокобезопасный `HashMap`, но **без блокировки всей карты**. Замок берётся только на отдельную корзину (бакет) при записи, а чтение вообще без замков. Поэтому много потоков работают параллельно, не мешая друг другу.

**Детали:** `null` ключи/значения запрещены (нельзя отличить «нет ключа» от «значение null» при конкуренции); `compute`/`merge` атомарны по ключу; `size()` приблизительный.

**Аналогия.** Вместо одного замка на всю библиотеку — замок на каждую полку: читатели разных полок не мешают друг другу.

**🔍 Если копнут глубже:**
- **До Java 8** ConcurrentHashMap делил данные на 16 «сегментов», и замок брался на сегмент (Segment, наследник ReentrantLock). С Java 8 от сегментов отказались — теперь CAS + synchronized на головном узле конкретного бакета, конкуренция ещё мельче.
- `size()` приблизителен, потому что считается из распределённых счётчиков (`baseCount` + `counterCells`) — точный подсчёт под конкуренцией был бы узким местом.
- Атомарные `compute`/`merge`/`computeIfAbsent` держат замок бакета на время функции — **не делай внутри них долгих/блокирующих операций** (заблокируешь бакет).
- `ConcurrentHashMap` даёт **слабосогласованный** итератор (не кидает `ConcurrentModificationException`), отражает состояние «где-то между» началом и концом обхода.

**Зачем.** Любимый вопрос. Главное: блокировка на уровне бакета, а не всей карты.

### 18. ThreadLocal — зачем и в чём опасность

**Простыми словами.** `ThreadLocal` — «личный ящик у каждого потока»: у каждого своя копия значения. Удобно хранить контекст запроса, данные пользователя.

**Опасность в пулах потоков.** Потоки в пуле живут долго и переиспользуются. Если не очистить `ThreadLocal`, значение «протечёт» в следующую задачу другого пользователя (утечка данных + памяти). Поэтому **обязательно `remove()` в finally**.

```java
try {
    userContext.set(currentUser);
    process();
} finally {
    userContext.remove();   // иначе протечёт в следующий запрос на этом потоке
}
```

**Зачем.** Реальный баг безопасности в банках (чужие данные в чужом запросе). Запомни про `remove()`.

## Современное (Java 21+)

### 19. Виртуальные потоки (virtual threads)

**Простыми словами.** Обычные потоки «тяжёлые» — их можно создать лишь тысячи. Виртуальные потоки (Java 21) — «лёгкие»: их можно миллионы. Когда виртуальный поток ждёт ввод-вывод (запрос к БД, сети), он «отцепляется» и не занимает реальный поток.

**Когда выгодны.** Для задач, которые **много ждут IO** (типичный веб-сервер: «поток на каждый запрос» снова работает отлично). Для тяжёлых вычислений (CPU) выигрыша нет.

**Важно.** Их **не нужно пулить** — создавай на каждую задачу. Подвох: `synchronized` с блокирующим вызовом внутри «прибивает» реальный поток — используй `ReentrantLock`.

**Зачем.** Современная тема, покажет актуальные знания.

## Типовые задачи и ловушки лайвкодинга

### 20. Почему счётчик из N потоков даёт меньше ожидаемого?

**Простыми словами.** Если N потоков делают `counter++` по 1000 раз, итог часто **меньше** N×1000. Причина: `i++` — это три действия (прочитать → прибавить → записать). Два потока читают одно значение, оба прибавляют, оба записывают — один инкремент «потерялся» (lost update).

**Аналогия.** Двое смотрят в блокнот «было 5», оба пишут «6». Должно было стать 7.

**Фикс:** `AtomicInteger.incrementAndGet()`, `LongAdder` или `synchronized`.

**Зачем.** Классическая задача на собесе. Умей объяснить, почему теряются инкременты.

### 21. Double-checked locking — почему нужен volatile

**Простыми словами.** Это паттерн «ленивого» создания одного объекта (синглтона) с двойной проверкой. Без `volatile` он **сломан**: строка `instance = new Config()` внутри может «переехать» так, что ссылка станет видна **до** того, как объект достроен. Второй поток схватит недостроенный объект.

```java
class Config {
    private static volatile Config instance;   // без volatile — баг!
    static Config getInstance() {
        if (instance == null) {                // первая проверка (без замка, быстро)
            synchronized (Config.class) {
                if (instance == null)          // вторая проверка (под замком)
                    instance = new Config();
            }
        }
        return instance;
    }
}

// ✅ проще и так же лениво — holder idiom (рекомендуемый способ):
class Config {
    private static class Holder { static final Config INSTANCE = new Config(); }
    static Config getInstance() { return Holder.INSTANCE; }
}
```

**Зачем.** Любимый senior-вопрос. Лучший ответ: «знаю про volatile в DCL, но обычно использую holder idiom — он проще и безопаснее».

## Как отвечать на собесе по многопоточности

1. **Начинай с аналогии** — «поток это работник», «synchronized это замок». Показывает понимание, а не зубрёжку.
2. **Две главные проблемы:** видимость (решает volatile/synchronized) и атомарность (решает Atomic/synchronized). Не путай их.
3. **Знай готовые инструменты** — обычно не надо писать руками wait/notify, есть `ConcurrentHashMap`, `AtomicInteger`, пулы.
4. **Банковский кейс** — перевод между счетами и deadlock: умей рассказать про порядок захвата замков.
