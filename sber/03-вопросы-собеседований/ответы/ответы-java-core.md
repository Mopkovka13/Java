## ООП и язык

### 1. Четыре принципа ООП

**Простыми словами.** ООП — способ организовать код так, будто это объекты из реального мира. Машина, пользователь, заказ — это объекты со своими данными и поведением. Четыре принципа — это правила, как этими объектами удобно пользоваться.

**Разбор каждого:**

- **Инкапсуляция** — «прячем внутренности, наружу торчат только кнопки». Как у телевизора: ты жмёшь кнопку на пульте, а что там внутри — не твоё дело. В коде: поля делаем `private`, а доступ даём через методы. Так никто снаружи случайно не сломает внутреннее состояние.

- **Наследование** — «новый класс берёт всё от родителя и добавляет своё». Как `СпортивнаяМашина extends Машина`: всё, что умеет машина, спортивная тоже умеет, плюс «турбо-режим».

- **Полиморфизм** — «один и тот же вызов работает по-разному в зависимости от объекта». Слово «полиморфизм» = «много форм». Ты говоришь `животное.голос()`, а кот мяукнет, собака гавкнет — решается **в момент выполнения** по реальному типу.

- **Абстракция** — «работаем с идеей, а не с деталями». Ты думаешь «мне нужно отправить уведомление», а не «мне нужно открыть SMTP-соединение». Описываешь *что* нужно (интерфейс), не привязываясь к *как*.

**Пример:**
```java
Notifier n = new SmsNotifier(); // переменная типа Notifier — это абстракция (контракт «умею слать»)
n.send(msg);                    // полиморфизм: в рантайме вызовется именно SmsNotifier
// Захотим email — заменим на new EmailNotifier(), и вызывающий код менять не надо
```

**Зачем.** Это фундамент. Без понимания ООП непонятна вся Java. На собесе проси приводить примеры — «расскажите про полиморфизм на вашем коде».

### 2. SOLID — пять принципов хорошего кода

**Простыми словами.** SOLID — пять правил, чтобы код было легко менять и не страшно трогать. Каждая буква — отдельное правило.

- **S — Single Responsibility (одна ответственность).** У класса должна быть одна причина меняться. Аналогия: швейцарский нож, который ещё и кофе варит — неудобно чинить. Не смешивай «построить отчёт» и «отправить его на почту» в одном классе.

- **O — Open/Closed (открыт для расширения, закрыт для изменения).** Добавляешь новое поведение **новым классом**, а не правишь старый рабочий код. Меньше шанс сломать то, что работало.

- **L — Liskov Substitution (подстановка Барбары Лисков).** Если код работает с родителем, он должен так же корректно работать с любым наследником, без сюрпризов. Классический «плохой» пример: `Квадрат extends Прямоугольник` — у квадрата ширина=высота, и код, ожидавший прямоугольник, ломается.

- **I — Interface Segregation (разделение интерфейсов).** Лучше несколько маленьких интерфейсов, чем один огромный. Не заставляй класс реализовывать методы, которые ему не нужны (робот не должен «есть»).

- **D — Dependency Inversion (инверсия зависимостей).** Зависим от **абстракций** (интерфейсов), а не от конкретных классов. Именно это делает Spring через внедрение зависимостей (DI).

**Пример на каждую букву:**
```java
// S — Single Responsibility: одна причина меняться
class ReportService {                 // ❌ и строит отчёт, и шлёт письмо — две причины
    byte[] buildReport() {...}
    void sendByEmail(byte[] r) {...}
}
// ✅ разделили: ReportBuilder (строит) + EmailSender (отправляет)

// O — Open/Closed: новое поведение новым классом, а не правкой старого
double fee(Payment p) {               // ❌ новый тип платежа = лезем в этот метод
    if (p.type() == CARD) return 0.01;
    if (p.type() == SBP)  return 0.00;
    throw new IllegalStateException();
}
// ✅ interface FeePolicy { BigDecimal fee(Payment p); }
//    новый тип = новый класс-реализация, старый код не трогаем

// L — Liskov: наследник заменяет родителя без сюрпризов
class Rectangle { void setWidth(int w){...} void setHeight(int h){...} }
class Square extends Rectangle {      // ❌ у квадрата setWidth обязан менять и высоту —
}                                     //    код, работавший с Rectangle, сломается
// ✅ не наследовать, а ввести общий интерфейс Shape { int area(); }

// I — Interface Segregation: узкие интерфейсы вместо одного «толстого»
interface Worker { void work(); void eat(); } // ❌ робот вынужден реализовать eat()
// ✅ два узких: interface Workable { void work(); }  interface Eatable { void eat(); }

// D — Dependency Inversion: зависим от абстракции, не от реализации
class OrderService {
    private final SmsClient sms = new SmsClient(); // ❌ зашита конкретная реализация
}
// ✅ зависим от интерфейса, реализацию подставит Spring
class OrderService {
    private final Notifier notifier;
    OrderService(Notifier notifier) { this.notifier = notifier; }
}
```

**Зачем.** SOLID спрашивают почти всегда. Главное — не вызубрить буквы, а уметь привести пример нарушения и как починить.

### 3. Интерфейс vs абстрактный класс

**Простыми словами.** И то, и другое нельзя создать напрямую (`new`). Разница: интерфейс — это «контракт, что объект *умеет*», абстрактный класс — «общий шаблон того, чем объект *является*».

**Подробнее:**
| | Интерфейс | Абстрактный класс |
|---|---|---|
| Сколько можно наследовать | много (`implements A, B, C`) | только один (`extends`) |
| Своё состояние (поля) | нет (только константы) | да, обычные поля |
| Конструктор | нет | есть |
| Смысл | «умеет летать» (Flyable) | «является птицей» (Bird) |

С Java 8 у интерфейсов появились `default`-методы (с реализацией), но это для обратной совместимости, не повод путать их с классами.

**Пример:**
```java
interface Flyable { void fly(); }          // умение
abstract class Bird { abstract void sing(); int wings = 2; } // сущность с состоянием

class Eagle extends Bird implements Flyable {
    void sing() {...}
    public void fly() {...}
}
```

**Зачем.** Очень частый вопрос. Запомни мостик: «умеет» → интерфейс, «является» → абстрактный класс.

### 4. Перегрузка (overload) vs переопределение (override)

**Простыми словами.** Перегрузка — **несколько методов с одним именем, но разными параметрами** в одном классе. Переопределение — **наследник заменяет метод родителя** своей версией.

**Ключевая разница — когда выбирается метод:**
- Перегрузка решается **на компиляции**, по типу переменной (статическому).
- Переопределение решается **в рантайме**, по реальному объекту.

**Пример (тонкое место):**
```java
class A {
    void print(Object o) { System.out.println("A: Object"); }
    void print(String s) { System.out.println("A: String"); } // перегрузка
}
class B extends A {
    @Override void print(Object o) { System.out.println("B: Object"); } // переопределение
}

A b = new B();
Object x = "строка";   // тип переменной — Object
b.print(x);            // "B: Object" — перегрузка выбрана по типу Object ещё на компиляции,
                       //               а переопределение сработало в рантайме
```

**Зачем.** Любят давать как «угадай вывод». Запомни: компилятор смотрит на **тип переменной**, чтобы выбрать перегрузку, рантайм — на **реальный объект** для переопределения.

### 5. static и final

**Простыми словами.**
- `static` — «принадлежит классу, а не конкретному объекту». Один на всех. Например, счётчик созданных объектов.
- `final` — «нельзя менять». Для переменной — нельзя переприсвоить, для метода — нельзя переопределить, для класса — нельзя наследовать.

**Важная ловушка:** `final` у переменной-ссылки запрещает менять **ссылку**, но **сам объект менять можно**.

**Пример:**
```java
final List<String> list = new ArrayList<>();
list.add("ok");            // ✅ можно — меняем содержимое объекта
list = new ArrayList<>();  // ❌ ошибка компиляции — нельзя переприсвоить ссылку

static int count;          // одно поле на весь класс, общее для всех объектов
```

**Зачем.** `static`/`final` встречаются в каждом проекте (константы, утилитные методы). Ловушка с `final List` — частый вопрос на внимательность.

### 6. Иммутабельный (неизменяемый) класс

**Простыми словами.** Иммутабельный объект — это объект, который после создания **нельзя изменить**. Как купюра: номинал зафиксирован. Хочешь другое значение — создаёшь новый объект. Пример из JDK — `String`.

**Как сделать:**
1. класс `final` (чтобы не переопределили через наследника);
2. все поля `private final`;
3. нет сеттеров;
4. если внутри есть изменяемые объекты (списки) — делать **защитные копии** на входе и выходе.

**Пример:**
```java
public final class Money {
    private final BigDecimal amount;
    private final List<String> tags;

    public Money(BigDecimal amount, List<String> tags) {
        this.amount = amount;
        this.tags = List.copyOf(tags); // копия: снаружи список потом не подменят
    }
    public List<String> tags() { return tags; } // List.copyOf уже неизменяемый
}
```

**Зачем.** Иммутабельные объекты **безопасны в многопоточке** (их нельзя испортить из другого потока), их можно спокойно класть в `HashMap` как ключи. Тема прямо связана с многопоточностью.

### 7. String pool, intern(), почему String неизменяемый

**Простыми словами.** Одинаковые строковые литералы Java хранит в одном месте — «пуле строк» — и переиспользует один объект, чтобы экономить память. Поэтому два литерала `"java"` — это физически **один и тот же объект**.

**Важно про сравнение:**
- `==` сравнивает «это один и тот же объект в памяти?»
- `equals()` сравнивает «одинаковое содержимое?»
- Строки **всегда** сравнивай через `equals()`.

**Пример:**
```java
String a = "java", b = "java";
a == b;            // true — оба из пула, один объект
String c = new String("java");
a == c;            // false — new создал отдельный объект
a == c.intern();   // true — intern() вернул объект из пула
a.equals(c);       // true — а так правильно сравнивать всегда
```

Почему String неизменяемый: безопасность (нельзя подменить путь к файлу после проверки), потокобезопасность, кеширование хеша, и сам пул возможен только с неизменяемыми строками.

**Зачем.** `==` для строк — классический баг новичка. На собесе обязательно покажи понимание разницы `==` и `equals`.

### 8. Ловушка Integer == Integer

**Простыми словами.** Java кеширует маленькие `Integer` от −128 до 127 (создаёт их заранее и переиспользует). Поэтому для маленьких чисел `==` случайно даёт `true`, а для больших — `false`. Это ловушка.

**Пример:**
```java
Integer a = 127, b = 127;
a == b;          // true  — взяты из кеша, один объект
Integer c = 128, d = 128;
c == d;          // false — два разных объекта (вне кеша)
c.equals(d);     // true  — а так правильно

Integer e = null;
int f = e;       // NullPointerException! распаковка null в int падает
```

**Зачем.** Обёртки (`Integer`, `Long`) сравнивай только через `equals`. Это реальный баг из задачи Сбера «найди 8 багов».

### 9. Type erasure (стирание типов) в дженериках

**Простыми словами.** Дженерики (`List<String>`) существуют только на этапе компиляции — компилятор проверяет типы и **стирает** их. В рантайме `List<String>` и `List<Integer>` — просто `List`. Информации о `String`/`Integer` уже нет.

**Что из этого следует (нельзя):**
- `new T()` — нельзя, тип неизвестен в рантайме;
- `new T[]` — нельзя;
- `if (obj instanceof List<String>)` — нельзя, такой проверки в рантайме нет.

**Зачем такой странный дизайн.** Чтобы старый код (до дженериков, Java 1.4) продолжал работать. Это компромисс ради совместимости.

**Зачем знать.** Объясняет, почему некоторые «очевидные» вещи с дженериками не компилируются.

### 10. PECS и wildcards (`? extends` / `? super`)

**Простыми словами.** Когда метод принимает коллекцию «чего-то наследного от T», нужно решить: мы из неё **читаем** или в неё **пишем**? Правило-запоминалка **PECS**: *Producer Extends, Consumer Super*.

- `? extends T` — коллекция **отдаёт** нам элементы (producer, мы читаем). Писать нельзя — неизвестно, какой именно подтип внутри.
- `? super T` — коллекция **принимает** наши элементы (consumer, мы пишем). Читать можно только как `Object`.

**Пример:**
```java
List<? extends Number> producer = List.of(1, 2.0);
Number n = producer.get(0); // ✅ читаем — точно Number
producer.add(3);            // ❌ нельзя: вдруг это List<Double>?

List<? super Integer> consumer = new ArrayList<Number>();
consumer.add(42);           // ✅ пишем Integer — точно влезет
Object o = consumer.get(0); // читаем только как Object
```

**Зачем.** Тема для middle+. Достаточно понимать логику «читаю → extends, пишу → super».

### 11. Records, sealed, pattern matching (Java 17/21)

**Простыми словами.** Новые удобства современной Java:

- **record** — короткий способ создать класс-«коробку для данных». Одна строка вместо 50: поля, конструктор, `equals`, `hashCode`, `toString` генерируются сами. Идеален для DTO (объектов передачи данных).
- **sealed** — «закрытая семья классов»: явно перечисляешь, кто может наследоваться (`permits`). Компилятор знает всех — это даёт безопасный `switch` без `default`.
- **pattern matching** — проверка типа с одновременной распаковкой: `if (o instanceof Person p)` — сразу получаешь `p`, без ручного приведения.

**Пример:**
```java
public record Transfer(String from, String to, BigDecimal amount) {
    public Transfer { // компактный конструктор для валидации
        if (amount.signum() <= 0) throw new IllegalArgumentException();
    }
}

sealed interface PaymentResult permits Success, Declined {}
record Success(String id) implements PaymentResult {}
record Declined(String reason) implements PaymentResult {}

String text = switch (result) {     // default не нужен — компилятор знает всех
    case Success s  -> "ok: " + s.id();
    case Declined d -> "отказ: " + d.reason();
};
```

Java 21 добавила виртуальные потоки (см. многопоточность) и sequenced collections.

**Зачем.** Покажет, что ты знаешь современную Java, а не только версию 8.

## Контракты (фирменная тема Сбера)

### 12. Контракт equals()

**Простыми словами.** `equals()` решает, «считаются ли два объекта одинаковыми». Чтобы он работал предсказуемо, должен соблюдать правила:

- **рефлексивность** — объект равен сам себе (`x.equals(x)` = true);
- **симметричность** — если `x равен y`, то и `y равен x`;
- **транзитивность** — если `x=y` и `y=z`, то `x=z`;
- **консистентность** — повторные вызовы дают тот же результат;
- `x.equals(null)` всегда `false`.

**Зачем.** Если нарушить эти правила, объекты будут странно вести себя в коллекциях (теряться, дублироваться).

### 13. Связь equals и hashCode

**Простыми словами.** `hashCode()` — это «номер ячейки» (бакета), куда `HashMap` кладёт объект. Правило: **если два объекта равны по equals, у них обязан быть одинаковый hashCode**. Иначе объект «потеряется».

**Аналогия.** Представь камеру хранения: `hashCode` — номер шкафчика. Положил вещь в шкафчик №5, а ищешь в №8 (потому что hashCode вернул другое число) — не найдёшь, хотя вещь есть.

**Пример бага:**
```java
class Key {
    final int id;
    Key(int id) { this.id = id; }
    @Override public boolean equals(Object o) { return o instanceof Key k && k.id == id; }
    // hashCode НЕ переопределён → у равных ключей разные хеши!
}
Map<Key, String> map = new HashMap<>();
map.put(new Key(1), "value");
map.get(new Key(1)); // null! искали не в том бакете
```

**🔍 Если копнут глубже:**
- **Изменяемый ключ — ловушка:** положил объект в `HashMap`, потом изменил у него поле, влияющее на `hashCode` → объект «теряется» (он в старом бакете, ищется в новом). Ключи должны быть иммутабельными.
- **Число 31 в `hashCode`** (`31 * result + field`) — нечётное простое, и `31 * x` JVM оптимизирует в сдвиг `(x << 5) - x`. Удобно и даёт хорошее распределение.
- `Objects.hash(a, b, c)` удобен, но создаёт временный массив (varargs) — в горячем коде иногда пишут хеш вручную.
- Хороший `hashCode` должен **равномерно распределять** значения: плохой (например, всегда возвращающий поле, которое часто совпадает) ведёт к коллизиям и деградации (см. вопрос 14).

**Зачем.** Правило «переопределяешь equals — переопредели и hashCode» спрашивают постоянно. Объект в `HashMap` без этого ломается.

### 14. Что если hashCode() всегда возвращает константу?

**Простыми словами.** Формально правило не нарушено (равные объекты дают равный хеш — ведь хеш у всех один). Но тогда **все объекты падают в один бакет**, и `HashMap` превращается из «быстрого поиска» в «перебор списка». Скорость падает с O(1) до O(n).

**Аналогия.** Все вещи свалили в один шкафчик — теперь, чтобы найти нужную, перебираешь всё.

**Зачем.** Это «тихая» проблема: код работает правильно, но медленно. Тоже из задачи «8 багов».

### 15. Контракт compareTo и связь с TreeMap

**Простыми словами.** `compareTo()` определяет порядок сортировки (меньше/равно/больше). `TreeMap`/`TreeSet` (отсортированные коллекции) считают два элемента **равными, если `compareTo` вернул 0** — а НЕ по `equals`. Если они расходятся — элементы могут «исчезать».

**Классический пример:**
```java
var values = List.of(new BigDecimal("1.0"), new BigDecimal("1.00"));
new HashSet<>(values).size();  // 2 — equals видит разный масштаб (1.0 ≠ 1.00)
new TreeSet<>(values).size();  // 1 — compareTo считает их равными, второй «пропал»
```

**Зачем.** Тонкое место, любят на senior. Главное запомнить: в `TreeSet`/`TreeMap` «равенство» = `compareTo == 0`.

### 16. Serializable vs Externalizable

**Простыми словами.** Сериализация — превращение объекта в байты (чтобы сохранить в файл/отправить по сети).

- **Serializable** — «пометь класс, и Java сама всё сделает» через рефлексию. Поля с `transient` не сохраняются. `serialVersionUID` — номер версии для проверки совместимости.
- **Externalizable** — «пишешь руками» (`writeExternal`/`readExternal`). Полный контроль, но требует **публичный конструктор без аргументов**, и порядок чтения должен зеркалить порядок записи (иначе данные перепутаются — главный баг задачи Сбера).

**Зачем.** В банках сериализация важна (передача между системами). Запомни про порядок чтения=записи и про transient.

### 17. Почему clone() — антипаттерн

**Простыми словами.** Метод `clone()` в Java сделан неудобно: нужно реализовать «пустой» интерфейс `Cloneable` (иначе ошибка в рантайме), по умолчанию он копирует **поверхностно** (вложенные объекты остаются общими), плохо дружит с `final`-полями и наследованием.

**Что использовать вместо.** Копирующий конструктор `new Order(other)` или статический метод `Order.copyOf(other)` — понятнее и надёжнее.

**Зачем.** Покажет зрелость: знаешь не только «как», но и «почему так не делают».

## Коллекции

### 18. Как устроен HashMap

**Простыми словами.** `HashMap` — это массив «корзин» (бакетов). Чтобы понять, в какую корзину положить ключ, считается его `hashCode`, и по нему вычисляется индекс. Если в одну корзину попало несколько ключей (коллизия) — они хранятся списком, а при большом количестве (8+) список превращается в дерево для скорости.

**Детали для ответа:**
- индекс бакета = `(размер − 1) & hash`;
- при заполнении на 75% (load factor 0.75) массив увеличивается вдвое (resize);
- размер всегда степень двойки — чтобы битовое `&` работало как быстрый остаток от деления.

**Схема:**
```
индекс бакета = (n-1) & hash
 ┌───┬───┬───┬───┬───┬───┐
 │ 0 │ 1 │ 2 │ 3 │ 4 │...│   ← массив бакетов
 └───┴─┬─┴───┴─┬─┴───┴───┘
       │       └─ ("Иван"→1)                       один ключ
       └─ ("Пётр"→2) → ("Анна"→3) → ...            коллизия: связный список,
                                                   при 8+ узлах превращается в дерево
```

**Аналогия.** Гардероб с пронумерованными секциями: по номеру (хешу) сразу идёшь в нужную секцию, а не перебираешь весь гардероб.

**🔍 Если копнут глубже:**
- Список в бакете превращается в **красно-чёрное дерево** при ≥ 8 узлах, но только если всего бакетов ≥ 64 (иначе сначала resize). Обратно в список — при ≤ 6 (гистерезис, чтобы не «дёргалось»).
- **Почему размер — степень двойки:** тогда `(n-1) & hash` эквивалентно `hash % n`, но битовое «И» намного быстрее деления.
- **Resize** при превышении load factor: создаётся массив ×2, все ключи перераскладываются (rehash) — дорогая операция, поэтому полезно задавать начальную ёмкость, если знаешь размер.
- В **Java 7** при многопоточном resize мог образоваться зацикленный список (вечный цикл в `get`). В Java 8 переписали — такого нет, но HashMap всё равно **не потокобезопасен** (для конкурентного доступа — `ConcurrentHashMap`).
- Fail-fast достигается полем `modCount`: итератор запоминает его и кидает `ConcurrentModificationException`, если коллекцию изменили мимо него.

**Зачем.** «Расскажи, как устроен HashMap» — топ-вопрос на любом Java-собесе.

### 19. ArrayList vs LinkedList

**Простыми словами.**
- **ArrayList** — это массив. Быстро берёт элемент по индексу (`get` за O(1)), но вставка в середину медленная (надо сдвигать).
- **LinkedList** — цепочка элементов, каждый знает соседа. Быстро вставлять/удалять (если уже на месте), но `get(i)` медленный — надо идти по цепочке.

**На практике.** ArrayList почти всегда быстрее, потому что массив лежит в памяти подряд (процессору удобнее). LinkedList нужен редко.

**Аналогия.** ArrayList — пронумерованные полки (сразу к нужной). LinkedList — поезд из вагонов (чтобы дойти до 10-го, пройди первые 9).

**Зачем.** Просят сравнить и спросят «что выберешь?» — ответ: обычно ArrayList.

### 20. HashMap vs TreeMap vs LinkedHashMap

**Простыми словами.** Все три — словари «ключ→значение», разница в порядке:
- **HashMap** — порядок не гарантирован, самый быстрый (O(1)).
- **TreeMap** — ключи всегда **отсортированы** (дерево, O(log n)), ключи должны уметь сравниваться (Comparable).
- **LinkedHashMap** — помнит **порядок вставки** (или порядок обращения — тогда из него легко сделать LRU-кеш).

**Зачем.** «Нужен отсортированный словарь?» → TreeMap. «Нужен порядок добавления?» → LinkedHashMap.

### 21. Как устроен HashSet

**Простыми словами.** `HashSet` — это `HashMap` под капотом, где твои элементы лежат в роли ключей, а значение — одна общая заглушка. Поэтому у `HashSet` те же свойства: уникальность по equals/hashCode, скорость O(1), один `null`.

**Зачем.** Показывает понимание, что Set — обёртка над Map.

### 22. Fail-fast vs fail-safe итераторы

**Простыми словами.** Что будет, если менять коллекцию во время прохода по ней циклом?
- **Fail-fast** (ArrayList, HashMap) — сразу падает с `ConcurrentModificationException`, чтобы ты заметил ошибку.
- **Fail-safe** (CopyOnWriteArrayList, ConcurrentHashMap) — работает по копии/снимку, не падает.

**Как правильно удалять в цикле:**
```java
for (Integer x : list)
    if (x == 2) list.remove(x); // ❌ ConcurrentModificationException

list.removeIf(x -> x == 2);     // ✅ правильно (или через iterator.remove())
```

**Зачем.** Реальная ошибка, которую все совершают. Запомни `removeIf`.

### 23. Сложности операций (Big-O)

**Простыми словами.** Big-O — «насколько замедлится операция, когда данных станет много». O(1) — мгновенно независимо от размера; O(n) — пропорционально размеру; O(log n) — очень медленный рост.

**Шпаргалка:**
- ArrayList: `get` O(1), добавить в конец ≈ O(1), вставить в середину O(n).
- HashMap/HashSet: в среднем O(1), в худшем O(log n).
- TreeMap/TreeSet: O(log n).
- LinkedList: вставка по месту O(1), доступ по индексу O(n).

**Зачем.** Спросят «какая сложность поиска в HashMap» — отвечай O(1) в среднем.

## JVM и память

### 24. Структура памяти JVM

**Простыми словами.** Где Java хранит данные:
- **Heap (куча)** — все объекты (всё, что создано через `new`). Делится на «молодое» поколение (новые объекты) и «старое» (выжившие).
- **Stack (стек)** — у каждого потока свой; хранит вызовы методов и локальные переменные. Закончился вызов — память освободилась сама.
- **Metaspace** — информация о самих классах.

**Схема:**
```
┌──────────────────── HEAP (общая для всех потоков) ─────────────────────┐
│  Young Generation                      │  Old Generation               │
│  ┌────────┬───────────┬───────────┐    │  ┌─────────────────────────┐  │
│  │  Eden  │ Survivor 0│ Survivor 1│    │  │ долгоживущие объекты    │  │
│  └────────┴───────────┴───────────┘    │  └─────────────────────────┘  │
└────────────────────────────────────────────────────────────────────────┘
┌─ STACK (свой у КАЖДОГО потока) ─┐   ┌─ METASPACE ──────────────┐
│ фреймы вызовов + локальные пер. │   │ метаданные классов       │
└─────────────────────────────────┘   └──────────────────────────┘
```

**Две частые ошибки:**
- `StackOverflowError` — переполнили стек (обычно бесконечная рекурсия).
- `OutOfMemoryError` — закончилась куча (слишком много объектов).

**Зачем.** Помогает понимать, почему программа падает и как это чинить.

### 25. Как работает сборщик мусора (GC)

**Простыми словами.** GC сам удаляет объекты, на которые больше никто не ссылается, — тебе не нужно вручную освобождать память. Работает на наблюдении: **большинство объектов умирает молодыми** (создали в методе — и забыли). Поэтому молодое поколение чистится часто и дёшево, старое — редко.

**Сборщики (можно просто назвать):**
- **G1** — по умолчанию, баланс, предсказуемые паузы;
- **ZGC / Shenandoah** — сверхкороткие паузы для больших куч;
- **Parallel** — максимальная пропускная способность.

**Схема (жизнь объекта):**
```
 new ──> [Eden] ──minor GC──> [Survivor] ──пережил N сборок──> [Old Gen]
            │                      │                              │
            └─ большинство умирает здесь ──────── major/full GC (реже) ──┘
```

**Аналогия.** Уборщик, который чаще проверяет «стол новичков» (там быстро появляется мусор) и реже — «архив».

**🔍 Если копнут глубже:**
- **G1** делит кучу не на сплошные young/old, а на множество **регионов** одинакового размера и собирает в первую очередь самые «мусорные» (Garbage First). Цель — уложиться в заданную паузу (`-XX:MaxGCPauseMillis`).
- **Stop-the-world (STW)** — momenты, когда приложение замирает на время работы GC. Современные сборщики (ZGC/Shenandoah) делают большую часть работы конкурентно, паузы < 10 мс даже на больших кучах.
- **Humongous objects** в G1 — объекты больше половины региона, размещаются особо и могут провоцировать full GC.
- **Full GC** — самый тяжёлый: чистит всю кучу со «stop-the-world». Частые full GC — тревожный симптом (мало памяти/утечка).
- Полезные флаги: `-Xms`/`-Xmx` (границы кучи), `-XX:+UseG1GC`/`UseZGC`, логи GC через `-Xlog:gc*`.

**Зачем.** Спросят «как работает GC» — расскажи про поколения и что память освобождается автоматически.

### 26. Виды ссылок (strong, soft, weak, phantom)

**Простыми словами.** Насколько крепко объект «держится» за жизнь:
- **Strong** (обычная ссылка) — пока есть, объект жив всегда.
- **Soft** — GC удалит, только если **кончается память**. Хорошо для кешей.
- **Weak** — GC удалит при **первой же уборке**. Используется в `WeakHashMap`.
- **Phantom** — для отслеживания момента удаления (редко).

**Зачем.** Тема про кеши и утечки памяти, для middle+.

### 27. Как искать утечку памяти

**Простыми словами.** Утечка — когда объекты, которые уже не нужны, кто-то продолжает держать, и GC не может их удалить. Память растёт, в итоге `OutOfMemoryError`.

**Как ловить:**
1. снять «снимок памяти» (heap dump) — например, флагом `-XX:+HeapDumpOnOutOfMemoryError`;
2. открыть в анализаторе (Eclipse MAT) и посмотреть, **кто держит ссылки** на лишнее.

**Частые причины:** статические коллекции, которые только растут; кеши без срока жизни; незакрытые ресурсы; `ThreadLocal` в пулах потоков.

**Зачем.** Практический вопрос на senior. Достаточно описать симптом + инструмент + типовые причины.

### 28. JIT-компиляция

**Простыми словами.** Сначала Java выполняет байткод «интерпретируя» (медленно). «Горячие» методы (которые вызываются часто) JIT компилирует в быстрый машинный код прямо во время работы. Поэтому JVM «разгоняется» после старта.

**Следствие.** Нельзя замерять скорость на «холодной» JVM — для бенчмарков есть инструмент JMH.

**Зачем.** Объясняет, почему «прогрев» важен и почему первые запросы медленнее.

### 29. Иерархия загрузчиков классов (classloaders)

**Простыми словами.** Классы грузятся тремя загрузчиками по цепочке: **Bootstrap** (ядро JDK) → **Platform** → **Application** (твой код). Действует правило «сначала спроси родителя» (делегирование).

**Тонкость.** Один и тот же класс, загруженный разными загрузчиками, считается **разными** классами — отсюда странные `ClassCastException` в серверах приложений.

**Зачем.** Редкий, но «отсеивающий» вопрос для senior.

### 30. JVM в контейнере (Docker/Kubernetes)

**Простыми словами.** Раньше JVM в контейнере видела память всего сервера, а не лимит контейнера, и падала. Сейчас (по умолчанию) JVM учитывает лимиты контейнера.

**Что важно:**
- задавай `-Xmx` примерно в 75% от лимита памяти (остальное — на классы, стеки, нативную память), иначе контейнер убьют (OOMKilled, код 137) без диагностики;
- мало выделенных CPU → JVM создаёт маленькие пулы потоков → медленнее.

**Зачем.** Очень актуально — все деплоят в Kubernetes. Сильный практический ответ.

## Исключения

### 31. Checked vs unchecked исключения

**Простыми словами.**
- **Checked** (наследники `Exception`, кроме Runtime) — компилятор **заставляет** их обработать или объявить. Для ситуаций, от которых можно «оправиться» (файл не найден).
- **Unchecked** (наследники `RuntimeException`) — ошибки программиста (`NullPointerException`, выход за границы). Компилятор не заставляет ловить.

**Важно для Spring:** `@Transactional` по умолчанию откатывает транзакцию только на **unchecked** исключениях.

**Зачем.** Спросят разницу и «когда какие бросать». Связка со Spring — бонус.

### 32. try-with-resources

**Простыми словами.** Конструкция, которая **сама закрывает ресурсы** (файлы, соединения), даже если случилась ошибка. Не нужно писать `finally { ... close() }` вручную.

**Пример:**
```java
try (var conn = dataSource.getConnection();
     var stmt = conn.prepareStatement(sql)) {
    // работаем
} // conn и stmt закроются автоматически, в обратном порядке
```
Закрываются в порядке, обратном открытию. Ресурс должен реализовать `AutoCloseable`.

**Зачем.** Стандарт работы с ресурсами. Покажет, что не забываешь их закрывать.

### 33. finally и return

**Простыми словами.** Блок `finally` выполняется **всегда** (кроме `System.exit` или падения JVM). Но если в `finally` написать `return` или бросить исключение — он «перебьёт» результат из `try`. Так делать не надо.

**Зачем.** Каверзный вопрос «что вернётся». Запомни: `finally` сильнее `try`, но класть туда `return` — антипаттерн.

### 34. Как строить иерархию исключений в проекте

**Простыми словами.** Создай своё базовое доменное исключение, а от него — подвиды по смыслу (`NotFound`, `Validation`, `Integration`), каждому дай код ошибки. В одном месте (`@RestControllerAdvice` в Spring) переводи их в HTTP-ответы.

**Правила:** не «глотать» исключения молча, не логировать одно и то же дважды, при оборачивании сохранять причину (`cause`).

**Зачем.** Практический senior-вопрос про дизайн обработки ошибок.

## Stream API и функциональные интерфейсы

### 35. Промежуточные vs терминальные операции

**Простыми словами.** Stream — это «конвейер» обработки коллекции.
- **Промежуточные** (`map`, `filter`, `sorted`) — ленивые, только описывают, что делать, и ничего не запускают.
- **Терминальные** (`collect`, `forEach`, `count`) — запускают весь конвейер и дают результат.

Без терминальной операции конвейер не выполнится. Stream **одноразовый** — повторно использовать нельзя.

**Пример:**
```java
list.stream()
    .filter(x -> x > 0)   // промежуточная (ленивая)
    .map(x -> x * 2)      // промежуточная
    .collect(toList());   // терминальная — здесь всё и выполнится
```

**Зачем.** Базовое понимание Stream, спрашивают часто.

---

### 36. map vs flatMap

**Простыми словами.**
- **map** — превращает каждый элемент в другой (1 → 1).
- **flatMap** — каждый элемент превращает в **поток** и «склеивает» всё в один плоский поток. Нужен, когда у тебя «список списков» и хочется один общий список.

**Пример:**
```java
orders.stream().map(Order::getItems)             // Stream<List<Item>> — список списков
orders.stream().flatMap(o -> o.getItems().stream()) // Stream<Item> — единый плоский поток
       .map(Item::price)
       .reduce(BigDecimal.ZERO, BigDecimal::add);
```

**Аналогия.** map — переложить содержимое каждой коробки в новую коробку. flatMap — высыпать всё из всех коробок в одну кучу.

**Зачем.** Любимый вопрос про Stream. Запомни: «список списков → один список» = flatMap.

---

### 37. Ловушка Collectors.toMap

**Простыми словами.** `toMap` падает с ошибкой, если встретит **два одинаковых ключа** (не знает, какое значение оставить). Решение — указать правило слияния третьим аргументом.

**Пример:**
```java
// ❌ два клиента с одним email → IllegalStateException
clients.stream().collect(toMap(Client::email, c -> c));
// ✅ правило: при конфликте оставить первого
clients.stream().collect(toMap(Client::email, c -> c, (a, b) -> a));
// ✅ или если дубликаты ожидаемы — группируем
clients.stream().collect(groupingBy(Client::email));
```

**Зачем.** Реальная ошибка в проде. Запомни про merge-функцию.

### 38. Когда нельзя parallelStream

**Простыми словами.** `parallelStream` распараллеливает обработку, но это часто **вредит**:
- источник плохо делится (LinkedList);
- операции меняют общее состояние (гонки данных);
- элементов мало или операции дешёвые (накладные расходы съедают выигрыш);
- **главное на сервере:** все parallelStream делят один общий пул на всю JVM — один «тяжёлый» затормозит всех.

**Зачем.** На сервере parallelStream почти всегда плохая идея — сильный ответ.

### 39. Как правильно использовать Optional

**Простыми словами.** `Optional` — «коробка, в которой может быть значение, а может не быть». Сделан, чтобы метод честно говорил «я могу ничего не найти», вместо возврата `null`.

**Правила:**
- используй как **возвращаемый тип** метода поиска;
- **не используй** для полей, параметров, коллекций (для коллекции лучше пустой список);
- вместо `.get()` используй `.orElseThrow()`, `.map()`, `.orElseGet()`.

**Зачем.** Помогает избегать `NullPointerException`. Спросят «зачем Optional» — ответ: явно показать возможное отсутствие значения.

### 40. Основные функциональные интерфейсы

**Простыми словами.** Это интерфейсы с одним методом, чтобы передавать «кусок логики» как лямбду:
- **Function<T,R>** — берёт T, возвращает R (`apply`);
- **Supplier<T>** — ничего не берёт, возвращает T (`get`);
- **Consumer<T>** — берёт T, ничего не возвращает (`accept`);
- **Predicate<T>** — берёт T, возвращает true/false (`test`).

**Ссылки на методы** — короткая запись лямбды: `String::valueOf`, `list::add`, `ArrayList::new`.

**Пример:**
```java
Predicate<String> notEmpty = s -> !s.isBlank();
Function<String, Integer> length = String::length;
Supplier<List<String>> newList = ArrayList::new;
```

**Зачем.** Основа лямбд и Stream API. Запомни хотя бы эти четыре.

## Как отвечать на собесе по Java Core

1. **Сначала смысл, потом детали.** «HashMap — это массив корзин…» лучше, чем сразу про load factor.
2. **Всегда давай пример** — свой код или короткий фрагмент.
3. **Связывай с практикой:** equals/hashCode → HashMap, иммутабельность → многопоточность, checked → Spring транзакции.
4. **Не уверен — рассуждай вслух**, это ценится больше, чем заученная фраза.
