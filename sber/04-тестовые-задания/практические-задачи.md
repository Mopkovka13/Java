# Практические задачи (middle / senior) — условие → решение

Это задачи «посложнее лайвкодинга»: проектирование маленького компонента, многопоточность, работа с дизайном. Их дают на middle/senior-секциях Сбера, Яндекса, Ozon, VK. Источники — внизу.

Каждая задача: **Задача → Идея → Решение → Сложность → На что смотрит интервьюер**.

---

## 1. LRU-кэш (классика, спрашивают очень часто)

**Задача.** Реализовать кэш фиксированного размера с вытеснением **least recently used** (давно не используемых). Операции `get`/`put` за O(1). При переполнении удаляется элемент, к которому дольше всего не обращались.

**Идея.** Нужна структура, дающая и быстрый доступ по ключу (хеш-таблица), и порядок использования (двусвязный список). В Java это уже совмещено в `LinkedHashMap` с `accessOrder=true` — достаточно переопределить `removeEldestEntry`.

**Решение (короткое, на собесе оценят знание JDK).**
```java
class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    LruCache(int capacity) {
        super(16, 0.75f, true);   // accessOrder=true → порядок по обращению, не вставке
        this.capacity = capacity;
    }
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;  // когда вернёт true — самый старый удалится
    }
}
```

**Решение «руками» (если просят без LinkedHashMap)** — HashMap + двусвязный список: `get` находит узел по ключу и переносит его в голову; `put` добавляет в голову, при переполнении удаляет хвост. Узел хранит prev/next, чтобы перенос был за O(1).

**Сложность.** `get`/`put` — O(1), память O(capacity).
**На что смотрит интервьюер.** Понимаешь ли, почему именно «хеш + связный список»; знаешь ли готовый `LinkedHashMap`; что делать с потокобезопасностью (обернуть в `Collections.synchronizedMap` или взять Caffeine).

## 2. Rate Limiter (ограничитель запросов)

**Задача.** Не больше N вызовов за период T (например, 5 запросов в минуту на пользователя). Потокобезопасно.

**Идея.** Самый частый алгоритм — **token bucket («ведро токенов»)**: в ведре N токенов, каждый вызов тратит один, токены пополняются со временем. Закончились — отказ. Простой вариант для собеса — **sliding window log**: хранить времена вызовов, выбрасывать старше T, проверять размер.

**Решение (sliding window, наглядно).**
```java
class RateLimiter {
    private final int maxCalls;
    private final long windowMs;
    private final Deque<Long> calls = new ArrayDeque<>();

    RateLimiter(int maxCalls, long windowMs) {
        this.maxCalls = maxCalls;
        this.windowMs = windowMs;
    }
    synchronized boolean allow() {
        long now = System.currentTimeMillis();
        while (!calls.isEmpty() && now - calls.peekFirst() >= windowMs) {
            calls.pollFirst();              // выбрасываем вызовы старше окна
        }
        if (calls.size() < maxCalls) {
            calls.addLast(now);
            return true;
        }
        return false;                       // лимит исчерпан
    }
}
```

**Сложность.** `allow` амортизированно O(1), память O(maxCalls).
**На что смотрит интервьюер.** Потокобезопасность (`synchronized`/атомарность); знание алгоритмов (token bucket vs sliding window vs fixed window и их минусы — у fixed window граничный всплеск ×2). Бонус: как сделать распределённо → счётчики в Redis (атомарный `INCR + EXPIRE` или Lua-скрипт), ответ `429 Too Many Requests` + `Retry-After`.

## 3. Сжатие массива в диапазоны (VK, реальная задача)

**Задача.** `[1, 4, 5, 2, 3, 9, 8, 11, 0]` → `"0-5,8-9,11"`. Подряд идущие числа схлопнуть в диапазон.

**Идея.** Отсортировать, убрать дубликаты, пройти одним проходом, отслеживая начало и конец текущего диапазона.

**Решение.**
```java
static String compress(int[] a) {
    if (a.length == 0) return "";
    int[] s = Arrays.stream(a).distinct().sorted().toArray();
    StringBuilder sb = new StringBuilder();
    int start = s[0], prev = s[0];
    for (int i = 1; i <= s.length; i++) {
        if (i < s.length && s[i] == prev + 1) {     // диапазон продолжается
            prev = s[i];
        } else {                                     // диапазон закончился — выводим
            if (sb.length() > 0) sb.append(',');
            sb.append(start == prev ? String.valueOf(start) : start + "-" + prev);
            if (i < s.length) { start = s[i]; prev = s[i]; }
        }
    }
    return sb.toString();
}
```

**Сложность.** Время O(n log n) (сортировка), память O(n).
**На что смотрит интервьюер.** Аккуратность с граничными случаями: пустой массив, последний диапазон (его легко «забыть» вывести), одиночное число (без дефиса), дубликаты.

## 4. Система фильтрации уведомлений (Яндекс, middle/senior)

**Задача.** Уведомление: `(id, тип, получатель, текст)`. Перед отправкой нужно: проверить разрешённые каналы пользователя, проверить блокировки, сделать **дедупликацию за 24 часа** (не слать одинаковое дважды).

**Идея.** Это задача на **дизайн**, а не на алгоритм. Ключевое: выделить абстракции (источник настроек, хранилище истории) и собрать **pipeline фильтров** — так легко добавлять новые правила.

**Решение (каркас).**
```java
interface NotificationFilter {
    boolean allow(Notification n);   // true — пропустить дальше
}

class ChannelFilter implements NotificationFilter {   // канал разрешён пользователю?
    private final UserSettings settings;
    public boolean allow(Notification n) { return settings.allows(n.recipient(), n.type()); }
}

class DeduplicationFilter implements NotificationFilter {  // не было такого же за 24ч?
    private final SentHistory history;     // например, Redis с TTL=24ч
    public boolean allow(Notification n) {
        String key = n.recipient() + ":" + n.type() + ":" + n.text().hashCode();
        return history.putIfAbsent(key, Duration.ofHours(24));  // true если ключа не было
    }
}

class NotificationService {
    private final List<NotificationFilter> filters;   // цепочка, легко расширять
    void send(Notification n) {
        for (NotificationFilter f : filters) {
            if (!f.allow(n)) return;     // любой фильтр может отсеять
        }
        deliver(n);
    }
}
```

**На что смотрит интервьюер.** Чистые абстракции и расширяемость (новый фильтр = новый класс — это Open/Closed); где хранить историю дедупликации (Redis с TTL — естественный выбор); идемпотентность; что делать при сбое доставки (retry/DLQ). Это уже ближе к system design.

## 5. Worker Pool с graceful shutdown (многопоточность)

**Задача.** Пул из N воркеров принимает задачи через очередь и обрабатывает их параллельно. При остановке — доработать принятые задачи и корректно завершиться.

**Идея.** Готовый `ExecutorService` уже делает это: `submit` кладёт задачи, `shutdown` + `awaitTermination` — мягкое завершение.

**Решение.**
```java
ExecutorService pool = Executors.newFixedThreadPool(N);

for (Task t : tasks) {
    pool.submit(() -> process(t));      // задачи разбираются N потоками
}

pool.shutdown();                        // новые задачи не принимаем, начатые доделываем
if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
    pool.shutdownNow();                 // не успели — прерываем принудительно
}
```

**На что смотрит интервьюер.** Разница `shutdown` (мягко) vs `shutdownNow` (прерывает); зачем `awaitTermination`; в проде — ограниченная очередь и политика отказа (см. [многопоточность, вопрос 11](../03-вопросы-собеседований/ответы/ответы-многопоточность.md)).

## 6. Топ-N из огромного файла (потоковая обработка, Ozon)

**Задача.** Файл 10 ГБ со строками (например, URL логов). Найти топ-10 самых частых, **не загружая файл в память**.

**Идея.** Читать построчно (стримом), считать частоты в `HashMap`, держать топ-10 в куче (`PriorityQueue`) фиксированного размера. Если уникальных значений тоже слишком много — внешняя сортировка / map-reduce по чанкам.

**Решение (каркас).**
```java
Map<String, Long> freq = new HashMap<>();
try (Stream<String> lines = Files.lines(Path.of("huge.log"))) {  // ленивое чтение
    lines.forEach(line -> freq.merge(line, 1L, Long::sum));
}
// топ-10 через min-heap размера 10
PriorityQueue<Map.Entry<String, Long>> heap =
    new PriorityQueue<>(Map.Entry.comparingByValue());
for (var e : freq.entrySet()) {
    heap.offer(e);
    if (heap.size() > 10) heap.poll();   // выкидываем наименьший — остаются топ-10
}
```

**Сложность.** Время O(n log 10) ≈ O(n), память O(уникальных) для счётчиков + O(10) для кучи.
**На что смотрит интервьюер.** Что не грузишь всё в память (`Files.lines`, а не `readAllLines`); куча вместо полной сортировки; что делать, если даже счётчики не влезают (разбить на чанки, частичные агрегаты, объединить — идея map-reduce).

## Как готовиться к практическим задачам

1. **Сначала уточни требования** (объёмы, потокобезопасность, распределённость) — для middle+ это половина оценки.
2. **Выдели абстракции** до кода — интерфейсы, ответственность классов.
3. **Знай, что уже есть в JDK** — `LinkedHashMap` (LRU), `BlockingQueue`, `ExecutorService`, `PriorityQueue`. Изобретать велосипед — минус.
4. **Назови, как масштабировать** решение (Redis, шардинг, map-reduce) — это поднимает грейд ответа.
5. **Связывай с проектом** — где у тебя были кэш, лимиты, очереди.
